                                ABSTRACT


             Large-language-model applications are evolving from single-turn
chat interfaces into systems that plan, use tools, preserve context, and coordinate
multiple specialised agents. However, application developers commonly re-
build scheduling, memory, event propagation, execution monitoring, and failure
handling for each project. This report presents AgentOS, a hybrid multi-agent
runtime environment that provides these operating-system-style services around
autonomous AI applications. The implemented system combines a Next.js user
interface, a FastAPI gateway, a Redis-backed event path, MongoDB task history,
ChromaDB semantic retrieval, structured LLM planning, dependency-aware di-
rected acyclic graph execution, semantic context paging, a global priority-aging
scheduler, hybrid local/cloud model routing, token and concurrency admission
control, and a sandboxed Python code runner with bounded self-healing retries.
The frontend exposes the generated plan graph and live scheduler and execution
activity through WebSocket updates. The report distinguishes implemented fa-
cilities from proposed components such as complete role-based access control
and durable coroutine restoration after a kernel restart. Verification is based on
repository compile checks, TypeScript checks, and focused smoke tests rather
than unsubstantiated performance claims. AgentOS therefore provides a modu-
lar foundation for studying reliable, observable, and resource-aware multi-agent
execution.


             Keywords: multi-agent runtime, semantic planning, DAG execution,
context paging, priority scheduling.

                               CHAPTER 1

                           INTRODUCTION


1.1       BACKGROUND


           Large-language-model (LLM) applications have progressed from re-
active question-answering interfaces to systems that can plan, call tools, main-
tain memory, and delegate work to specialised agents. A useful multi-agent ap-
plication therefore needs more than a prompt and a model endpoint. It needs a
runtime that can represent work, enforce dependencies, manage limited provider
and execution resources, preserve useful context, report progress, and recover
safely from failures.


           Operating-system concepts provide a useful design analogy. A task is
submitted to a gateway, a planner decomposes it into executable steps, a sched-
uler selects runnable agent work, a resource manager performs admission con-
trol, and an event path exposes state transitions. AgentOS applies this analogy
to LLM-powered agents while retaining the uncertainty and latency of model
calls.


1.2       MOTIVATION


           In a conventional chatbot, application logic, conversation state, tool
invocation, and error handling are often tightly coupled. This makes it difficult
to run independent work concurrently or to explain why an agent was selected.
Long conversations also exceed the practical context window of a model, while
blindly truncating history can remove information needed by later steps. Finally,
unrestricted execution services and tools create safety and observability risks.
                                                                                2


           AgentOS is motivated by the need for a reusable runtime layer. The
project investigates how planning, agent retrieval, DAG execution, semantic
context paging, global scheduling, resource accounting, event streaming, and
sandboxed execution can be composed into one observable system.


1.3       PROBLEM STATEMENT


           There is no single lightweight runtime in the project environment
that coordinates heterogeneous agents across multiple concurrent tasks while
enforcing dependencies, observing token and concurrency budgets, preserving
relevant context, and exposing execution state to a user interface. Reimplement-
ing these facilities inside each application increases duplication, makes failures
difficult to diagnose, and prevents systematic evaluation of scheduling and re-
source policies.


1.4       OBJECTIVES


           The objectives of AgentOS are:


        1. Develop a modular AI-kernel-style runtime for specialised agents;

        2. Generate structured execution plans, retrieve suitable agents seman-
           tically, and validate their dependencies as a DAG;

        3. Manage bounded conversational context through semantic page-out
           and page-in using a vector-backed swap space;

        4. Schedule runnable work with priority aging, fairness, cooperative
           dispatch, concurrency limits, and token budgets; and

        5. Execute agent tasks reliably while publishing lifecycle events and
           measurable activity to the user interface.
                                                                                 3


1.5       SCOPE


           The current phase covers a Next.js frontend, FastAPI gateway,
Python kernel, Redis event transport, MongoDB task persistence, ChromaDB
retrieval, structured planning, DAG validation and Mermaid generation, context
paging, a global in-process scheduler, resource admission, hybrid local/cloud
model routing, and a registry of specialised agents for information, research,
documents, communication, calculation, and bounded execution tasks. The
scope does not claim complete RBAC, distributed scheduler workers, forced
termination of active LLM calls, or automatic coroutine restoration. These are
documented as future work.


1.6       CONTRIBUTIONS


           The project contributions are a unified execution model for heteroge-
neous agents, a visible plan graph, a Redis-mediated activity stream, a semantic
context paging mechanism, a priority-aging scheduler with resource admission,
and a bounded execution and recovery path for specialised agents. The imple-
mentation also makes a deliberate distinction between design aspirations and
features that are present and testable in the repository.


1.7       REPORT ORGANIZATION


           Chapter 2 reviews related work on autonomous agents, memory,
planning, scheduling, tool use, security, event transport, and vector retrieval.
Chapter 3 presents the AgentOS architecture and data flows, while Chapter 4
describes its algorithms, storage, events, and verification evidence. Chapter 5
reports the evaluation protocol and results for context paging, planner tool selec-
tion, and agent scheduling. The conclusion synthesises the findings and future
work; the appendix documents the registered agents and internal workflows.

                                CHAPTER 2

                      LITERATURE SURVEY


2.1       OVERVIEW


           This chapter reviews work that informs the design of AgentOS. The
survey combines peer-reviewed or archival research with official technical doc-
umentation for infrastructure components. Each group is considered in terms of
its contribution, limitation for the present project, and the way AgentOS uses or
extends the idea.



2.2       AGENT RUNTIMES AND AUTONOMOUS AGENTS


           AIOS frames an LLM agent operating system around schedul-
ing, context management, memory, storage, access control, and tool man-
agement [1]. Its operating-system analogy directly motivates the AgentOS
kernel, although the current AgentOS implementation is smaller and uses a
Python/Redis/MongoDB stack rather than a complete OS abstraction. The
broader survey by Wang et al. classifies LLM-based agents by construction,
applications, and evaluation [2]; it identifies coordination and reliability as open
challenges that AgentOS addresses through explicit events and DAG dependen-
cies.


           The LLM-as-an-OS proposal treats models as system resources and
agents as applications [3]. AutoGen demonstrates programmable multi-agent
conversation and human-in-the-loop patterns [4], while LangGraph provides
graph-based orchestration and durable execution concepts [5]. These systems
                                                                                 5


show the value of explicit state and orchestration, but do not provide the exact
global priority-aging and token-admission policy implemented here.


           AgentBench provides a complementary evaluation perspective by
testing language models as agents in eight interactive environments rather than
treating generation quality as the only outcome [6]. Its multi-turn, open-ended
tasks expose failures in long-horizon reasoning, decision making, and instruc-
tion following. This distinction is important for AgentOS: a plan may be syn-
tactically valid while the resulting tool calls, dependencies, or execution state
are still incorrect. AgentOS therefore evaluates planning and runtime behaviour
separately instead of presenting a single language-generation score as evidence
of system reliability.



2.3        MEMORY AND CONTEXT MANAGEMENT


           MemGPT introduces virtual context management that moves infor-
mation between active context and external storage [7]. MemoryOS organises
memory into short-, mid-, and long-term layers and evaluates memory retention
for conversational agents [8]. These works motivate AgentOS context page-out
and page-in. AgentOS uses semantic embeddings in ChromaDB and an active-
window policy; it currently provides a project-level paging mechanism rather
than a learned memory hierarchy or an independently benchmarked memory
score.


           Recent evaluation work also shows why memory retrieval should not
be reduced to isolated fact lookup. LongMemEval measures information ex-
traction, multi-session reasoning, temporal reasoning, knowledge updates, and
abstention in long-term interactive conversations [9]. These dimensions expose
failure modes that a single retrieval-recall value can hide, particularly when pre-
viously stored information becomes outdated or when the correct response is
                                                                               6


to abstain. The present AgentOS evaluation is deliberately narrower: it mea-
sures evidence visibility and retrieval metrics for the paging mechanism, while
answer-level judging and dynamic knowledge-update evaluation remain outside
the current scope.


           Retrieval-Augmented Generation (RAG) combines generation with a
non-parametric knowledge store [10]. ChromaDB documents collections, em-
beddings, and distance-based retrieval [11]. AgentOS uses this pattern both for
agent capability retrieval and for swapped context. The limitation is that re-
trieval quality depends on the embedding model and distance configuration; the
current implementation exposes similarity metadata but does not claim domain-
wide retrieval benchmarks.


           Recent evaluation frameworks further distinguish retrieval quality
from the quality of the final generated response. RAGAs evaluates retrieval rele-
vance, contextual faithfulness, and answer quality without requiring a complete
set of human reference answers [12]. ARES similarly separates context rele-
vance, answer faithfulness, and answer relevance, using synthetic training data
together with a small human-annotated set for calibration [13]. These studies
provide a useful direction for extending AgentOS: the present context-paging
experiments report evidence visibility and retrieval recall, while future evalua-
tions could add answer-level faithfulness and relevance measures without con-
flating them with page-in success.



2.4       PLANNING, TOOL USE, AND REFLECTION


           ReAct interleaves reasoning and action so that an agent can use ex-
ternal tools during problem solving [14]. Toolformer studies self-supervised
learning for deciding when and how to call APIs [15]. Generative Agents com-
bine memory, reflection, and planning for believable behaviour [16]. Reflexion
                                                                               7


uses verbal feedback to improve subsequent attempts without updating model
weights [17]. AgentOS adopts structured planning, explicit tool boundaries,
persisted events, and bounded self-healing, but does not train models or claim
the autonomous reflection capabilities of these research systems.


           ToolLLM and its ToolBench dataset study tool use at a substantially
larger scale, covering more than 16,000 real-world REST APIs across 49 cate-
gories and evaluating both API recommendation and multi-step call paths [18].
This work highlights that tool use depends on capability retrieval, argument
construction, and execution-path selection, not only on the model’s general rea-
soning ability. AgentOS addresses the same separation at a smaller system level
through a registered agent catalogue, semantic candidate retrieval, structured
plans, and an end-to-end tool-selection evaluation. The comparison is concep-
tual rather than numerical: AgentOS does not claim ToolBench-scale coverage
or model-training results.


           Recent survey work provides a useful vocabulary for positioning this
architecture within workflow-optimisation research. Yue et al. distinguish static
workflow templates from dynamic runtime graphs and separate reusable de-
signs, run-specific realised graphs, and execution traces [19]. They also argue
that workflow evaluation should consider graph structure, execution cost, ro-
bustness, and variation across inputs in addition to downstream task metrics.
This perspective supports AgentOS’s separation of planning, DAG validation,
scheduling, and runtime evidence, while also identifying graph-level optimisa-
tion and cost-aware evaluation as directions for future work.


           The Transformer architecture remains the dominant basis for modern
LLMs [20]. Its context limitation makes external context management relevant
to AgentOS, while the model itself remains an external provider selected by the
planner/runtime.
                                                                                  8


2.5       SCHEDULING, RESOURCES, AND RELIABILITY


           Classical operating-system scheduling shows why priority alone can
starve old work and why aging can improve fairness [21]. Linux cgroups pro-
vide a practical model for resource accounting and isolation [22]. AgentOS
adapts these ideas to agent work: effective priority increases with queue wait,
admission checks global and per-task slots, and token reservations are tracked
before dispatch. Unlike a CPU scheduler, AgentOS cannot forcibly preempt
an in-flight remote LLM request; its dispatch quantum is cooperative, with full
execution checkpoints remaining a future extension.


           The workflow and orchestration literature emphasises explicit depen-
dency graphs and stateful execution. LangGraph persistence documents check-
pointed graph state [23], while Temporal documents durable workflow execu-
tion [24]. AgentOS currently validates and executes a DAG in-process and
persists task/event evidence; automatic continuation of interrupted coroutines
remains future work.


2.6       SECURITY AND SANDBOXED EXECUTION


           The Model Context Protocol specifies a standard way for AI appli-
cations to connect models with tools and data sources [25]. OWASP’s LLM
security guidance highlights risks including excessive agency, insecure tool use,
and code execution [26]. Python subprocess execution and filesystem scoping
are therefore bounded in the code runner. Firecracker demonstrates the stronger
isolation achievable with microVMs [27]. AgentOS’s current runner limits du-
ration and output and scopes its working directory, but it is not a substitute for a
hardened kernel or microVM sandbox.


2.7       EVENT-DRIVEN INFRASTRUCTURE
                                                                                9


           Redis documents Pub/Sub as a low-latency message distribution
mechanism [28]. MongoDB provides durable document storage suitable for
task history and metadata [29]. AgentOS uses Redis for transient task/event
transport and queue metadata and MongoDB for durable task records. Redis
Pub/Sub alone is not a durable event log; recovery therefore persists relevant
state in Redis hashes and MongoDB events, with full replay and exactly-once
semantics left for future work.



2.8       RESEARCH GAP AND POSITIONING


           The reviewed systems provide strong solutions for individual con-
cerns: planning, memory, graph orchestration, tool use, security, or workflow
durability. AgentOS’s contribution is an integrated educational/runtime proto-
type that makes these concerns observable together in one project. Its distinctive
implementation choices are semantic agent selection, explicit DAG validation,
global priority-aging scheduling, token/concurrency admission, Redis lifecycle
events, context paging, and frontend graph/activity observability. The current
phase prioritises a transparent and testable architecture over claims of produc-
tion isolation or benchmark leadership.

                               CHAPTER 3

                           SYSTEM DESIGN


3.1       DESIGN PRINCIPLES


           AgentOS is designed as a modular runtime. The gateway handles
external requests, the orchestrator converts a prompt into a structured plan, and
the kernel owns execution concerns. Redis is used for low-latency coordination
and event transport, while MongoDB stores task history. ChromaDB stores em-
beddings used for semantic agent retrieval and context swap. The design keeps
the current dependency truth in the DAG executor and treats scheduler decisions
as admission and dispatch decisions.



3.2       OVERALL ARCHITECTURE


           As shown in Figure 3.1, AgentOS is organised as an overall runtime
architecture connecting the user interface, gateway, planner, kernel, storage,
tools, agents, and model engines. The figure combines implemented runtime
components with architectural modules that are planned or only partially imple-
mented; their implementation status is documented separately in Section 3.12.
A user submits a task through the Next.js interface. The FastAPI gateway cre-
ates or retrieves task state and communicates with the kernel. The planner se-
lects agents and creates steps; the kernel validates and executes those steps while
publishing activity events.

3.3       HYBRID LLM REASONING ENGINE


           AgentOS uses a privacy-aware hybrid reasoning engine to balance
cloud-model capability with local data protection. The model factory exposes
one LangChain-compatible facade to the planner, agents, and response gener-
ator, while the facade selects a provider for each invocation. Groq is used for
non-sensitive orchestration work when a cloud credential is configured; Ollama
is used for privacy-sensitive work such as local file inspection, repository or
code analysis, academic material, personal information, credentials, and other
locally scoped data. The local path is configured with an Ollama model such as
llama3.2 or qwen3:8b and communicates with the host-local Ollama service.


           The router applies conservative input classification before a model
call. It extracts text from strings, message lists, and structured inputs, then
checks privacy and local-resource indicators. A sensitive classification has
precedence over cloud routing, so the request remains local even when Groq is
available. The router also supports explicit local, cloud, and hybrid modes.
In hybrid mode, an unavailable or failed Groq request is retried through Ollama,
providing a local continuity path. This design makes the provider choice a ker-
nel concern rather than a frontend concern: the UI reports the decision emitted
by the kernel instead of attempting to infer privacy from the prompt.


           The same facade preserves structured-output and tool-binding inter-
faces. Consequently, planning, agent tool calls, and final response generation
can all use the routing policy without requiring separate graph implementations.
Each selected route produces an llm.ROUTED event containing the provider, sen-
sitivity flag, reason, and operation. These events are persisted with the task and
forwarded to the frontend, making the privacy boundary auditable during exe-
cution.

3.5        PLANNER AND DAG EXECUTION


            The planner retrieves relevant agent descriptions, requests a struc-

cycles, and supplies a sequential fallback only when a plan omits dependen-

summarises this path. The frontend uses the same validated plan to generate

3.6       CONTEXT PAGING


           The context pager keeps a bounded active message window. When
the window is exceeded, older or less relevant messages are embedded and
stored in the ChromaDB swap collection. A later query retrieves semantically
related pages and injects them into the active context. ChromaDB’s cosine space
returns distance; the implementation converts it as s = 1 − d, where d is the re-
turned cosine distance. Figure 3.4 presents the page-out and page-in flow. This

4.1       IMPLEMENTATION ENVIRONMENT


          The kernel is implemented in Python using asynchronous services.
The backend is FastAPI-based and the frontend is implemented with Next.js
and TypeScript. Redis provides task/event channels and scheduler metadata;
MongoDB stores task records and event history; ChromaDB provides per-
sistent vector collections for planning and context swap. The LLM layer is
provider-independent at the graph boundary: a hybrid model facade presents
one asynchronous LangChain interface while selecting Groq or Ollama per in-
vocation. Provider-specific LLM usage is treated as optional metadata because
some providers do not return reliable token counts.



4.2       SEMANTIC AGENT RETRIEVAL


          Agent descriptions are embedded in a persistent ChromaDB collec-
tion. A task description is used as a query, and the top candidate records are
returned with their distances and metadata. In the configured cosine space,
ChromaDB returns d = 1 − cos(θ), so the implementation reports s = 1 − d.
It does not divide by two; that transformation would be appropriate for a dif-
ferent distance normalisation. An LRU cache reduces repeated retrieval for
identical descriptions. Algorithm 4.1 summarises this candidate-retrieval and
cosine-distance conversion procedure.

4.3       PLANNER AND FALLBACK


           The planner asks the configured LLM for a structured execution plan.
The response is parsed into steps and normalised against the agent registry. If the
LLM request fails, exceeds quota, or produces invalid structure, a deterministic
fallback creates a usable plan from the best retrieved agent(s). This maintains
task execution and observability without pretending that the fallback has the
same reasoning quality as the provider.


           Figure 4.1 illustrates the complete optimised planning path, from se-
mantic candidate retrieval through structured plan validation, fallback routing,
DAG construction, scheduling, and runtime execution.

4.5       DAG VALIDATION


             Every step has a unique identifier and a list of prerequisite identi-
fiers. Validation rejects duplicate identifiers, unknown agents, unknown depen-
dencies, and cycles. A Kahn-style topological pass counts nodes removed from
the ready set. If the count is smaller than the number of steps, the dependency
graph contains a cycle and is rejected. The same validated dependency lists are
used to generate Mermaid edges. Algorithm 4.3 specifies the cycle-detection
procedure.

4.7         RESOURCE ADMISSION AND TOKEN BUDGETS


            The resource manager checks active global slots, active slots for the
task, and the cumulative estimated token reservation for the task. A tempo-
rary denial leaves work waiting; an exhausted task budget is converted into a
blocked/failed outcome rather than leaving the task silently pending. Actual
provider usage, when available, is recorded separately from estimated admis-
sion tokens. This distinction explains why a provider such as Groq may display
zero usage metadata even while the scheduler correctly enforces its configured
estimate.

4.9       CONTEXT PAGE-OUT AND PAGE-IN


           The pager moves messages from the active conversation state to a
persistent ChromaDB collection after a configured window is exceeded. Each
page stores message content, task metadata, and an embedding. On a later turn,
the current query is embedded and the collection is searched; selected messages
are reintroduced in relevance order. The implementation emits page-out and
page-in metrics, allowing the UI or logs to verify that paging occurred.



4.10       SANDBOXED EXECUTION AND SELF-HEALING
                                                                                28


           The code runner creates a scoped temporary script, launches it with
asyncio.create subprocess exec, captures stdout/stderr, and terminates the
subprocess after a strict timeout. Output size is limited to prevent unbounded
memory use. On a traceback, the error is supplied to the coder/tester agent and a
revised script is attempted, up to three times. The runner publishes line-oriented
output and final status as kernel events. No claim is made that an ordinary
subprocess is equivalent to a container or microVM security boundary.


4.11       FRONTEND OBSERVABILITY


           The task activity panel displays lifecycle events, scheduler state,
queue position, effective priority, waiting time, attempt number, resource de-
cisions, and token totals when provider metadata is present. It also displays the
latest hybrid routing decision as Groq / cloud or Ollama / local, including
a privacy-sensitive message when applicable. The llm.ROUTED events appear
in the live timeline and are persisted with task history, so the provider selected
for planning, agent execution, and response generation can be inspected after
completion. The plan graph modal displays the structured graph and Mermaid
source. Token fields distinguish input, output, total, and configured budget;
when the provider omits usage, the interface reports that the metadata is un-
available rather than inventing a count.

                               CHAPTER 5

      RESULTS AND PERFORMANCE ANALYSIS


           This chapter reports the evaluation of three AgentOS subsystems: the
context-paging engine, the model-backed planner, and the global agent sched-
uler. The results are presented in a consistent order. First, the reporting proto-
col defines the datasets, comparison conditions, and metrics. The chapter then
evaluates context paging, planner tool selection, and scheduler behaviour in se-
quence. The final section consolidates the findings and states the limitations of
the measurements.



5.1       REPORTING PROTOCOL


           The evaluations use fixed task or question sets, documented config-
urations, and reproducible scoring rules. For each experiment, the expected
evidence, tool set, or scheduler outcome was defined before the trial. Raw trial
records were retained so that aggregate values could be recomputed. Percent-
ages are pooled over the reported trials; latency values are reported using the
aggregate statistic available for each run, with percentile values used for queue-
ing measurements.


           The context-paging experiments use deterministic synthetic conver-
sations and a fixed pilot subset of the LoCoMo long-term conversational-
memory dataset and benchmark [30]. The planner experiment uses the Agen-
tOS function catalogue and a fixed 50-trial task-selection run. The scheduler
experiment uses deterministic smoke scenarios and seeded synthetic workloads.
These are project-level implementation and reliability evaluations, not claims of
production capacity or general performance.
                                                                              38


5.2       CONTEXT-PAGING ENGINE


           The context engine was evaluated using two complementary datasets.
The first is a deterministic synthetic smoke set designed to verify the paging
pipeline, telemetry, and comparison harness. The second is a pilot evaluation
derived from the LoCoMo benchmark. The configurations compare complete-
context access, recent-message truncation, vector retrieval, and AgentOS pag-
ing.


           The results are retrieval-oriented. A successful retrieval trial means
that the annotated evidence required to answer the question is visible in the
active context or is returned by the paging operation. This measure is intention-
ally separate from end-to-end language-model answer accuracy, which requires
a fixed answer model and judge and was not enabled for these runs.



5.2.1     Evaluation protocol


           All configurations used the same local ChromaDB embedding func-
tion, active context window, question text, conversation history, and candidate
budget within each dataset. The full-context configuration is a quality control:
it receives the complete conversation and therefore does not perform retrieval.
Recent truncation retains only the active window. Vector RAG performs direct
semantic retrieval, while AgentOS paging combines a larger semantic candi-
date pool with one-message neighbourhood expansion and a lightweight lexical
reranking stage.


           The synthetic run expanded five seed scenarios into a fixed local
smoke set and executed 400 configuration trials. The external run used a fixed
pilot subset of the official LoCoMo questions and executed 800 configuration
trials. The threshold sweep was retained as a sensitivity analysis rather than as
                                                                                    39


evidence that a threshold was universally optimal. Page-in and page-out laten-
cies, embedding-cache behaviour, token estimates, and raw trial records were
recorded for every configuration.



5.2.2         Synthetic smoke evaluation


              The synthetic evaluation checks whether the implementation can
page out older messages, retrieve relevant evidence, handle an absent fact
through abstention, and reduce the active prompt size. Table 5.1 reports the

5.5       INTEGRATED INTERPRETATION AND LIMITATIONS


           The context engine demonstrates measurable active-context reduc-
tion and improved retrieval over direct vector RAG on the LoCoMo pilot,
although the synthetic smoke set remains easier than the external conversa-
tional data. The planner achieves 76.0% end-to-end exact tool-set accuracy and
required-tool recall across 50 trials; its main failure mode is missing required
tool calls rather than provider unavailability. The scheduler preserves through-
put while substantially reducing high-priority queue waiting under contention.


           These results have important limitations. The context experiments
                                                                           47


use a deterministic synthetic set and a fixed LoCoMo pilot rather than the
complete benchmark; threshold selection is exploratory, and no answer-model
judging or confidence intervals were enabled. The planner evaluation uses an
AgentOS-specific task set and should not be generalized beyond that scope. The
scheduler benchmark uses deterministic service times and stubbed persistence,
so it is not a production-capacity claim. Accordingly, the findings establish
implementation behaviour under the stated conditions, not universal superi-
ority over alternative systems. Future work should evaluate held-out planner
tasks and thresholds, add answer judging, replace stubbed persistence, and use
production-like scheduler traces.

                               CHAPTER 6

           CONCLUSION AND FUTURE WORK


           This project presented AgentOS, a modular runtime for multi-agent
applications in which planning, semantic agent selection, DAG execution, con-
text management, scheduling, resource admission, sandboxed code execution,
provider routing, and frontend observability are treated as shared system ser-
vices. The implemented system connects the Next.js interface, FastAPI gateway,
Python kernel, planner, Redis event path, MongoDB task history, ChromaDB
retrieval, scheduler, resource manager, agent runtime, and frontend activity in-
terface into one observable execution pipeline.


           The implementation demonstrates that operating-system-inspired
services can be composed around heterogeneous agents without placing
scheduling, memory, execution, and observability logic inside each individual
agent. Structured plans and dependency validation provide predictable execu-
tion order; semantic context paging reduces the prompt context presented to
the model; priority aging and resource admission coordinate runnable work;
provider routing supplies local/cloud model selection; and bounded subprocess
execution provides a controlled path for coding and testing tasks. The frontend
activity stream makes these decisions visible to the user.


           The evaluation supports three specific conclusions. First, context
paging remained effective under the reported conditions: AgentOS achieved
98.0% retrieval success on the synthetic set and 35.0% on the LoCoMo pilot,
improving on direct vector retrieval by 13 percentage points on the latter. Sec-
ond, the planner selected the exact required tool set in 38 of 50 trials, giving
an end-to-end accuracy of 76.0%; the remaining failures were model tool-call
                                                                                49


failures rather than provider or transport errors. Third, the scheduler preserved
comparable throughput while reducing high-priority queue-wait P95 by approxi-
mately 68% in steady state and 78% under contention relative to FIFO. These re-
sults are bounded by the datasets, configurations, and instrumentation described
in Chapter 5.


           The current implementation also has defined limitations. Scheduler
dispatch is cooperative, provider token usage may be unavailable when metadata
is omitted, and restart recovery detects interrupted work without restoring every
active coroutine. The context and planner evaluations are limited in dataset
size and task diversity, while the scheduler benchmark uses deterministic work-
loads and stubbed persistence. Evaluation results should therefore be interpreted
together with their dataset scope, provider conditions, and telemetry coverage
rather than as universal claims of system performance.


           Future work will first address reliability and recovery. Durable restart
resumption should restore incomplete task state without duplicating completed
steps, while checkpoints inside long-running agents would strengthen coop-
erative suspension and continuation. Capability enforcement should also be
extended through explicit permission policies and stronger isolation where re-
quired.


           Further studies should use production-like arrival traces, non-stubbed
persistence, cost-aware local/cloud scheduling, and changing provider condi-
tions. The context and planner evaluations should include held-out conver-
sations, paraphrased tasks, answer-level judging, and larger repeated trials.
Broader tool-use scenarios and autonomous event triggers can then test gen-
eralisation beyond the current scope while preserving the separation of planner,
scheduler, runtime, persistence, routing, and observability layers.
