\chapter{\uppercase{Literature Survey}}
\label{ch:survey}

\section{\uppercase{AgentOS and Autonomous Agent Runtimes}}
This chapter reviews research and technical work relevant to AgentOS, including agent operating-system architectures and surveys of autonomous agents \cite{mei2024aios,wang2024survey}, multi-agent orchestration \cite{wu2023autogen}, and graph-based workflow execution \cite{langgraphdocs}. It also examines work on memory, planning, scheduling, security, and event-driven infrastructure. Each topic is discussed in terms of its contribution, its limitations in relation to this project, and how AgentOS applies or extends the underlying ideas.

\section{\uppercase{Agent Runtimes and Autonomous Agents}}
AIOS frames an LLM agent operating system around scheduling, context management, memory, storage, access control, and tool management \cite{mei2024aios}. Its operating-system analogy directly motivates the AgentOS kernel, although the current AgentOS implementation is smaller and uses a Python/Redis/MongoDB stack rather than a complete OS abstraction. The broader survey by Wang et al. classifies LLM-based agents by construction, applications, and evaluation \cite{wang2024survey}; it identifies coordination and reliability as open challenges that AgentOS addresses through explicit events and DAG dependencies.

The operating-system model for LLM-based agents treats models as system resources and agents as applications \cite{liu2023llmos}. AutoGen explores configurable multi-agent conversations, including workflows with human participation \cite{wu2023autogen}, while LangGraph supports graph-based orchestration and persistent workflow state \cite{langgraphdocs}. Together, these efforts show the value of representing agent coordination and state explicitly. AgentOS builds on this direction by combining dependency-aware execution with a global priority-aging scheduler and token-budget admission.

AgentBench provides a complementary evaluation perspective by testing language models as agents in eight interactive environments rather than treating generation quality as the only outcome \cite{liu2023agentbench}. Its multi-turn, open-ended tasks expose failures in long-horizon reasoning, decision making, and instruction following. This distinction is important for AgentOS: a plan may be syntactically valid while the resulting tool calls, dependencies, or execution state are still incorrect. AgentOS therefore evaluates planning and runtime behaviour separately instead of presenting a single language-generation score as evidence of system reliability.

\section{\uppercase{Memory and Context Management}}
MemGPT introduces virtual context management that moves information between active context and external storage \cite{packer2023memgpt}. MemoryOS organises memory into short-, mid-, and long-term layers and evaluates memory retention for conversational agents \cite{kang2025memoryos}. These works motivate AgentOS context page-out and page-in. AgentOS uses semantic embeddings in ChromaDB and an active-window policy; it currently provides a project-level paging mechanism rather than a learned memory hierarchy or an independently benchmarked memory score.

Recent evaluation work also shows why memory retrieval should not be reduced to isolated fact lookup. LongMemEval measures information extraction, multi-session reasoning, temporal reasoning, knowledge updates, and abstention in long-term interactive conversations \cite{wu2024longmemeval}. These dimensions expose failure modes that a single retrieval-recall value can hide, particularly when previously stored information becomes outdated or when the correct response is to abstain. The present AgentOS evaluation is deliberately narrower: it measures evidence visibility and retrieval metrics for the paging mechanism, while answer-level judging and dynamic knowledge-update evaluation remain outside the current scope.

Retrieval-Augmented Generation (RAG) combines generation with a non-parametric knowledge store \cite{lewis2020rag}. ChromaDB documents collections, embeddings, and distance-based retrieval \cite{chromadocs}. AgentOS uses this pattern both for agent capability retrieval and for swapped context. The limitation is that retrieval quality depends on the embedding model and distance configuration; the current implementation exposes similarity metadata but does not claim domain-wide retrieval benchmarks.

Evaluation frameworks such as RAGAs and ARES distinguish the quality of retrieved context from the quality of the generated answer. RAGAs provides reference-free measures for retrieval relevance, faithfulness, and answer quality \cite{es2024ragas}. ARES evaluates context relevance, answer faithfulness, and answer relevance, and uses synthetic training data with a small human-annotated set for calibration \cite{saadfalcon2024ares}. These frameworks suggest ways to extend AgentOS evaluation. The current context-paging experiments measure evidence visibility and retrieval performance; future work could also assess whether retrieved context supports faithful and relevant answers.

\section{\uppercase{Planning, Tool Use, and Reflection}}
ReAct interleaves reasoning and action so that an agent can use external tools during problem solving \cite{yao2023react}. Toolformer studies self-supervised learning for deciding when and how to call APIs \cite{schick2023toolformer}. Generative Agents combine memory, reflection, and planning for believable behaviour \cite{park2023generative}. Reflexion uses verbal feedback to improve subsequent attempts without updating model weights \cite{shinn2023reflexion}. AgentOS adopts structured planning, explicit tool boundaries, persisted events, and bounded self-healing, but does not train models or claim the autonomous reflection capabilities of these research systems.

ToolLLM and its ToolBench dataset study tool use at a substantially larger scale, covering more than 16,000 real-world REST APIs across 49 categories and evaluating both API recommendation and multi-step call paths \cite{qin2023toolllm}. This work highlights that tool use depends on capability retrieval, argument construction, and execution-path selection, not only on the model's general reasoning ability. AgentOS addresses the same separation at a smaller system level through a registered agent catalogue, semantic candidate retrieval, structured plans, and an end-to-end tool-selection evaluation. The comparison is conceptual rather than numerical: AgentOS does not claim ToolBench-scale coverage or model-training results.

Recent survey work provides a useful vocabulary for positioning this architecture within workflow-optimisation research. Yue et al. distinguish static workflow templates from dynamic runtime graphs and separate reusable designs, run-specific realised graphs, and execution traces \cite{yue2026workflow}. They also argue that workflow evaluation should consider graph structure, execution cost, robustness, and variation across inputs in addition to downstream task metrics. This perspective supports AgentOS's separation of planning, DAG validation, scheduling, and runtime evidence, while also identifying graph-level optimisation and cost-aware evaluation as directions for future work.

The Transformer architecture introduced an attention-based approach that underlies many modern large language models \cite{vaswani2017attention}. Because these models process inputs within finite context windows, AgentOS provides external context management to preserve and retrieve task information across execution steps. The language model itself remains an external provider selected by the planner and runtime.

\section{\uppercase{Scheduling, Resources, and Reliability}}
Classical operating-system scheduling shows why priority alone can starve old work and why aging can improve fairness \cite{silberschatz2018os}. Linux cgroups provide a practical model for resource accounting and isolation \cite{cgroupsv2}. AgentOS adapts these ideas to agent work: effective priority increases with queue wait, admission checks global and per-task slots, and token reservations are tracked before dispatch. Unlike a CPU scheduler, AgentOS cannot forcibly preempt an in-flight remote LLM request; its dispatch quantum is cooperative, with full execution checkpoints remaining a future extension.

The workflow and orchestration literature emphasises explicit dependency graphs and stateful execution. LangGraph persistence documents checkpointed graph state \cite{langgraphpersistence}, while Temporal documents durable workflow execution \cite{temporaldocs}. AgentOS currently validates and executes a DAG in-process and persists task/event evidence; automatic continuation of interrupted coroutines remains future work.

\section{\uppercase{Security and Sandboxed Execution}}
The Model Context Protocol specifies a standard way for AI applications to connect models with tools and data sources \cite{mcpdocs}. OWASP's LLM security guidance highlights risks including excessive agency, insecure tool use, and code execution \cite{owaspllm}. Python subprocess execution and filesystem scoping are therefore bounded in the code runner. Firecracker demonstrates the stronger isolation achievable with microVMs \cite{firecracker}. AgentOS's current runner limits duration and output and scopes its working directory, but it is not a substitute for a hardened kernel or microVM sandbox.

\section{\uppercase{Event-Driven Infrastructure}}
Redis documents Pub/Sub as a low-latency message distribution mechanism \cite{redispubsub}. MongoDB provides durable document storage suitable for task history and metadata \cite{mongodocs}. AgentOS uses Redis for transient task/event transport and queue metadata and MongoDB for durable task records. Redis Pub/Sub alone is not a durable event log; recovery therefore persists relevant state in Redis hashes and MongoDB events, with full replay and exactly-once semantics left for future work.

\section{\uppercase{Research Gap and Positioning}}
The reviewed systems provide strong solutions for individual concerns: planning, memory, graph orchestration, tool use, security, or workflow durability. AgentOS's contribution is an integrated educational/runtime prototype that makes these concerns observable together in one project. Its distinctive implementation choices are semantic agent selection, explicit DAG validation, global priority-aging scheduling, token/concurrency admission, Redis lifecycle events, context paging, and frontend graph/activity observability. The current phase prioritises a transparent and testable architecture over claims of production isolation or benchmark leadership.
