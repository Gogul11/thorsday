\chapter{\uppercase{Conclusion and Future Work}}
\label{chap:conclusion}

This project presented AgentOS, a modular runtime for multi-agent applications in which planning, semantic agent selection, DAG execution, context management, scheduling, resource admission, sandboxed code execution, provider routing, and frontend observability are treated as shared system services. The implemented system connects the Next.js interface, FastAPI gateway, Python kernel, planner, Redis event path, MongoDB task history, ChromaDB retrieval, scheduler, resource manager, agent runtime, and frontend activity interface into one observable execution pipeline.

The implementation demonstrates that operating-system-inspired services can be composed around heterogeneous agents without placing scheduling, memory, execution, and observability logic inside each individual agent. Structured plans and dependency validation provide predictable execution order; semantic context paging reduces the prompt context presented to the model; priority aging and resource admission coordinate runnable work; provider routing supplies local/cloud model selection; and bounded subprocess execution provides a controlled path for coding and testing tasks. The frontend activity stream makes these decisions visible to the user.

The evaluation supports three specific conclusions. First, context paging remained effective under the reported conditions: AgentOS achieved 98.0\% retrieval success on the synthetic set and 35.0\% on the LoCoMo pilot, improving on direct vector retrieval by 13 percentage points on the latter. Second, the planner selected the exact required tool set in 38 of 50 trials, giving an end-to-end accuracy of 76.0\%; the remaining failures were model tool-call failures rather than provider or transport errors. Third, the scheduler preserved comparable throughput while reducing high-priority queue-wait $P_{95}$ by approximately 68\% in steady state and 78\% under contention relative to FIFO. These results are bounded by the datasets, configurations, and instrumentation described in Chapter~5.

The current implementation also has defined limitations. Scheduler dispatch is cooperative, provider token usage may be unavailable when metadata is omitted, and restart recovery detects interrupted work without restoring every active coroutine. The context and planner evaluations are limited in dataset size and task diversity, while the scheduler benchmark uses deterministic workloads and stubbed persistence. Evaluation results should therefore be interpreted together with their dataset scope, provider conditions, and telemetry coverage rather than as universal claims of system performance.

Future work will first address reliability and recovery. Durable restart resumption should restore incomplete task state without duplicating completed steps, while checkpoints inside long-running agents would strengthen cooperative suspension and continuation. Capability enforcement should also be extended through explicit permission policies and stronger isolation where required.

Further studies should use production-like arrival traces, non-stubbed persistence, cost-aware local/cloud scheduling, and changing provider conditions. The context and planner evaluations should include held-out conversations, paraphrased tasks, answer-level judging, and larger repeated trials. Broader tool-use scenarios and autonomous event triggers can then test generalisation beyond the current scope while preserving the separation of planner, scheduler, runtime, persistence, routing, and observability layers.
