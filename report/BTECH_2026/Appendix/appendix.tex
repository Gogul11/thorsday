\chapter{\uppercase{Evaluation Framework and Metrics}}
\label{app:metrics}

This appendix defines the metrics used to evaluate AgentOS and reports the
controlled scheduler benchmark completed for this phase. The metrics specify
how planning quality, execution reliability, scheduling behaviour, resource
control, context paging, event delivery, and user-facing observability are
measured. The scheduler workload results are reported in Chapter~\ref{chap5};
the appendix retains the metric definitions and reporting protocol for
reproducible future experiments.

\section{\uppercase{Evaluation Notation}}
Let $N$ be the number of evaluated tasks, $S$ the number of planned steps, and $E$ the number of emitted events. For each task, the expected result, required agents, dependency relationships, and final status must be recorded before execution. A task is counted as successful only when its required output is produced and all mandatory steps complete without an unrecovered error.

\section{\uppercase{Context Paging and Retrieval Metrics}}
The context-paging experiment should compare a bounded-context run with a run in which the complete conversation is available.
\begin{itemize}
\item Page-out rate $=\frac{\text{messages paged out}}{\text{messages received}}$.
\item Page-in precision@$k$ $=\frac{\text{relevant pages among top-$k$ retrieved pages}}{k}$.
\item Page-in recall $=\frac{\text{relevant pages retrieved}}{\text{relevant pages required}}$.
\item Context-retrieval mean similarity $=\frac{1}{m}\sum_{j=1}^{m}s_j$, where $s_j=1-d_j$ and $d_j$ is the ChromaDB cosine distance.
\item Context token reduction $=1-\frac{\text{active-context tokens with paging}}{\text{full-context tokens}}$.
\item Paging latency $=T_{page\text{-}in}-T_{query}$.
\end{itemize}

\section{\uppercase{Event and Observability Metrics}}
Redis and WebSocket behaviour will be evaluated by correlating the event identifier and execution identifier in Redis, MongoDB, the backend stream, and the frontend activity log.
\begin{itemize}
\item Event delivery rate $=\frac{\text{events received by the intended consumer}}{E}$.
\item Event loss rate $=1-\text{event delivery rate}$.
\item Event duplication rate $=\frac{\text{duplicate event records}}{E}$.
\item Event ordering accuracy $=\frac{\text{lifecycle transitions observed in valid order}}{\text{observed lifecycle transitions}}$.
\item WebSocket propagation latency $=T_{frontend\ receives}-T_{kernel\ publishes}$.
\item Observability completeness $=\frac{\text{events containing all required fields}}{E}$.
\end{itemize}
The required event fields are task identifier, step identifier, agent name, execution identifier, status, timestamp, priority, effective priority, queue wait, and attempt number.

\section{\uppercase{Code Runner Safety Metrics}}
\begin{itemize}
\item Timeout enforcement rate $=\frac{\text{timed-out processes terminated within the policy window}}{\text{timed-out processes}}$.
\item Output-capture completeness $=\frac{\text{runs with correctly captured stdout and stderr}}{\text{runs}}$.
\item Self-healing repair success $=\frac{\text{failed scripts repaired within the retry limit}}{\text{failed scripts eligible for repair}}$.
\item Retry exhaustion rate $=\frac{\text{scripts still failing after the maximum retries}}{\text{failed scripts}}$.
\item Working-directory escape count: number of executions writing outside the configured working directory. The desired value is zero.
\end{itemize}

\subsection{Agent A1: System Information Agent}
Agent A1 gathers system information, including hardware, software, running
processes, services, environment values, and current resource state. It uses
the registered system-information tools and reports the collected state.
\AgentArchitectureDiagram{Agent A1}{system inspection and analysis}{system information tools}
\AgentFlowDiagram{Agent A1}{a system-state request}{inspect resources, processes, and configuration}{summarise system state clearly}

\subsection{Agent A2: Date and Time Agent}
Agent A2 handles current date, time, timezone, day-of-week, and location-aware
date and time queries. It relies on date and time tools whenever a current or
timezone-sensitive value is required.
\AgentArchitectureDiagram{Agent A2}{date, time, and timezone queries}{date and time tools}
\AgentFlowDiagram{Agent A2}{a date or time request}{resolve location and call the appropriate time tool}{return a precise date/time answer}

\subsection{Agent A3: Research Agent}
Agent A3 gathers factual, academic, scientific, historical, and technical
information. It uses Wikipedia and trusted web-search tools, prefers reliable
sources, and includes source links when available. It is instructed not to
fabricate facts, citations, or URLs.
\AgentArchitectureDiagram{Agent A3}{factual research and source verification}{Wikipedia and trusted web-search tools}
\AgentFlowDiagram{Agent A3}{a research or fact-checking request}{search, verify, and extract only relevant facts}{summarise findings with sources}

\subsection{Agent A4: File and Document Agent}
Agent A4 manages local files and documents. It can search, read, create,
modify, move, rename, compare, summarise, and classify supported files. Delete
operations are deliberately separated into a confirmation flow: the path is
verified, confirmation is requested, and deletion is not claimed before the
backend confirms it.
\AgentArchitectureDiagram{Agent A4}{file and document operations}{file, document, and confirmation tools}
\AgentFlowDiagram{Agent A4}{a file or document request}{inspect, transform, or request deletion confirmation}{return the file result or confirmation state}

\subsection{Content Creator Agent}
The Content Creator drafts and formats text such as reports, documentation,
emails, messages, articles, proposals, summaries, and social posts. It does
not send emails and does not use external tools for ordinary text generation.
\AgentArchitectureDiagram{Content Creator Agent}{drafting and text formatting}{language model; no external tool required}
\AgentFlowDiagram{Content Creator Agent}{a writing or formatting request}{select the requested genre and structure}{return only the completed content}

\subsection{Email Agent}
The Email Agent sends messages to recipients. It extracts the recipient,
subject, and body from the task and previous agent results, removes unresolved
placeholders, invokes the email-delivery tool, and returns its delivery
confirmation.
\AgentArchitectureDiagram{Email Agent}{email dispatch and delivery}{email delivery tools}
\AgentFlowDiagram{Email Agent}{a request to send email}{extract recipient, subject, and clean body; send}{return the delivery confirmation}

\subsection{Weather Agent}
The Weather Agent retrieves and reports current conditions and forecasts for a
specified location. It selects current-weather or forecast tools based on the
requested time horizon and presents the result with clear meteorological data.
\AgentArchitectureDiagram{Weather Agent}{current conditions and forecasts}{current-weather and forecast tools}
\AgentFlowDiagram{Weather Agent}{a weather request}{identify location and time horizon; call weather tool}{format temperature and forecast details}

\subsection{Loan EMI Calculator Agent}
The Loan EMI Calculator Agent computes loan instalments and produces an
amortisation schedule. It receives the financial parameters through the task,
uses the registered calculation tools, and returns a formatted financial
result.
\AgentArchitectureDiagram{Loan EMI Calculator Agent}{EMI and amortisation calculation}{loan calculation tools}
\AgentFlowDiagram{Loan EMI Calculator Agent}{a loan calculation request}{validate principal, rate, and tenure; calculate EMI}{return EMI and amortisation details}

\subsection{Crypto PnL Agent}
The Crypto PnL Agent calculates cryptocurrency trade profit or loss and return
on investment. It formats the calculation as an investment report and can save
the report through its registered tools.
\AgentArchitectureDiagram{Crypto PnL Agent}{crypto trade PnL and ROI}{crypto PnL and report tools}
\AgentFlowDiagram{Crypto PnL Agent}{a crypto trade analysis request}{process trades, fees, and prices; calculate PnL}{return a formatted investment report}

\subsection{Code Runner Agent}
The Code Runner Agent generates standalone Python programs, executes them in a
constrained runner, captures standard output and errors, and repairs failures
for at most three attempts. It reports success only when execution exits
successfully.
\AgentArchitectureDiagram{Code Runner Agent}{code generation and bounded repair}{sandboxed Python runner}
\AgentFlowDiagram{Code Runner Agent}{a coding or testing request}{generate and execute code; inspect output and traceback}{return output on success or bounded failure details}

\subsection{Agent Creator}
The Agent Creator handles capabilities that are not covered by registered
agents. It creates a new tool file, creates and registers a new agent, updates
the relevant registries, and executes the generated agent. In the current
registry it is available as an implementation but is disabled from the default
runtime registry until explicitly enabled.
\AgentArchitectureDiagram{Agent Creator}{agent and tool generation}{file creation and registry tools}
\AgentFlowDiagram{Agent Creator}{an unsupported specialised task}{create tools, create agent, register, and execute}{return the generated agent's result}

\section{\uppercase{Reporting Protocol}}
The evaluation shall use a fixed task set and a documented procedure for every configuration.

\begin{enumerate}
\item \textbf{Define and repeat the test.} Record the prompts, expected outputs, required agents, dependency relations, configuration, number of tasks, and number of independent repetitions. Keep the planner model, candidate limit, context window, scheduler limits, resource limits, and retry policy fixed within a comparison.

\item \textbf{Record raw evidence.} Store the task identifier, prompt, expected result, candidates, generated plan, validation result, lifecycle events, attempts, timestamps, resource decisions, token metadata, and final status. Retain raw events so metrics can be recomputed.

\item \textbf{Compute task-level outcomes.} Mark a trial as successful only when the expected result is produced and all mandatory steps complete. Record whether the trial failed, waited, was retried, used fallback planning, violated dependency order, or exceeded a resource limit.

\item \textbf{Aggregate and report.} Report accuracy, success, failure, retry, fallback, and violation measures as percentages. For latency, queue waiting time, token usage, and other continuous measurements, report the mean, median, standard deviation, and 95th percentile ($P_{95}$), together with the number of trials and tasks.

For a rate, use the pooled value $100\times(\sum\text{numerator}/\sum\text{denominator})$ and state how missing or timed-out observations were handled. A zero denominator must be reported as \textit{not applicable}, not as zero.

\item \textbf{Document annotations and usage.} Explain labels for expected agents or relevant context pages, including the annotation procedure and number of labelled tasks. Distinguish provider-reported token usage from estimated admission usage.
\end{enumerate}

Each configuration summary should therefore include task and repetition counts, success or accuracy rate, failure and retry rates, latency statistics, and relevant scheduler, resource, context-paging, and token-usage measures. No experimental values are reported in this appendix.
