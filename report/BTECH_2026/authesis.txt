                                ABSTRACT


             Large-language-model applications are evolving from single-turn
chat interfaces into systems that plan, use tools, preserve context, and coordinate
multiple specialised agents. However, application developers commonly re-
build scheduling, memory, event propagation, execution monitoring, and failure
handling for each project. This report presents AgentOS, a hybrid multi-agent
runtime environment that provides these operating-system-style services around
autonomous AI applications. The implemented system combines a Next.js user
interface, a FastAPI gateway, a Redis-backed event path, MongoDB task history,
ChromaDB semantic retrieval, structured LLM planning, dependency-aware di-
rected acyclic graph execution, semantic context paging, a global priority-aging
scheduler, hybrid local/cloud model routing, token and concurrency admission
control, and a sandboxed Python code runner with bounded self-healing retries.
The frontend exposes the generated plan graph and live scheduler and execution
activity through WebSocket updates. The report distinguishes implemented fa-
cilities from proposed components such as complete role-based access control
and durable coroutine restoration after a kernel restart. Verification is based on
repository compile checks, TypeScript checks, and focused smoke tests rather
than unsubstantiated performance claims. AgentOS therefore provides a modu-
lar foundation for studying reliable, observable, and resource-aware multi-agent
execution.


             Keywords: multi-agent runtime, semantic planning, DAG execution,
context paging, priority scheduling.

                                CHAPTER 1

                            INTRODUCTION


1.1        FROM OPERATING SYSTEMS TO AGENTOS


           Operating systems provide the shared software foundation between
computer hardware and applications. They manage processor time, memory,
files, input/output devices, and process execution while offering stable abstrac-
tions and enforcing boundaries between competing programs [21]. This coordi-
nation allows multiple applications to run on the same computer in a controlled
and observable manner.


           AI applications are increasingly moving beyond the conventional
chatbot model. An agent can receive a goal, decide what information or ac-
tion is required, call tools, inspect results, retain task-related context, and revise
its plan across several steps [2]. More complex tasks can be divided among
specialised agents, such as agents for information gathering, document analysis,
and result checking. This makes the system modular, but also requires explicit
agent selection, dependency management, execution tracking, and failure han-
dling.


           The coordination challenge becomes greater when agents share lim-
ited resources. Language-model calls consume time, tokens, context capacity,
and sometimes paid provider resources, while concurrent tasks may compete
for execution slots, memory, and tools. The runtime must decide which work
is ready, control resource access, preserve useful context, and explain why an
action succeeded, failed, waited, or was retried. Context management is particu-
larly important because retaining every previous message can exceed model lim-
                                                                               2


its, whereas removing older messages without retrieval may discard decisions or
evidence needed by later steps. Research on long-term memory therefore em-
phasises retrieving relevant evidence rather than simply storing large volumes
of text [7, 8].


            Execution must also remain understandable to users and developers.
A final answer alone does not show which agents were selected, which steps
are waiting on dependencies, whether a tool call failed, or how resources were
consumed. Structured lifecycle events and task records provide this visibili-
ty, supporting diagnosis, evaluation, and consistent policies for tool access and
execution limits.


            These requirements motivate an operating-system-inspired founda-
tion for AI agents. In this analogy, agents and tasks resemble applications and
processes, plans describe work and dependencies, scheduling selects executable
tasks, and context services manage information needed by later model call-
s. Resource-management services can enforce concurrency and token budgets,
while event mechanisms expose state changes. AIOS applies this perspective
to scheduling, memory, storage, and tool management, while MemGPT uses
operating-system ideas to manage information within a limited context win-
dow [1, 7]. However, AI runtimes must also account for probabilistic model
behaviour, slow or remote calls, and incomplete provider usage or failure infor-
mation.


            An Agent Operating System, or AgentOS, adapts these principles
into a runtime layer for planning and coordinating AI agents. It provides
shared services for task representation, agent selection, dependency validation,
scheduling, context management, resource admission, and execution-state re-
porting. It does not replace a conventional operating system; instead, it applies
selected operating-system concepts to applications that depend on language
                                                                               3


models, tools, and cooperating agents. This shared layer makes workflows
explicit and provides a common place to observe task progress while leaving
application goals and agent capabilities to the applications built on it.


           This project develops and evaluates such a runtime through Agen-
tOS. A user submits a task through a web interface, the planning layer converts
it into steps and selects specialised agents, and the kernel validates dependen-
cies before scheduling ready work. The system combines semantic agent re-
trieval, dependency-aware graph execution, context paging, concurrency and
token-budget admission, hybrid local/cloud model routing, and lifecycle events
visible to the user. Its implementation connects a Next.js frontend, FastAPI
gateway, Python kernel, Redis coordination and event transport, MongoDB task
persistence, and ChromaDB vector retrieval. Together, these components pro-
vide a reusable and observable runtime for applications in which agents plan,
use tools, and cooperate on multi-step tasks.



1.2       MOTIVATION


           AI applications are moving from single-turn assistants toward agents
that can plan, use tools, retain task context, and carry out work across multiple
steps. As these applications become more capable, their infrastructure needs
grow: developers must manage task state, choose suitable agents, coordinate
dependent and independent work, control access to shared resources, and handle
failures. When each application implements these mechanisms separately, the
resulting integrations can be difficult to reuse, extend, and inspect.


           The request-response model alone is also a poor fit for work that
must continue across steps or involve several agents. Agent workflows need
explicit lifecycle and dependency management so that work can be scheduled as
it becomes ready and its progress can be observed. They also need a deliberate
                                                                                4


context strategy: model context is limited, but simply discarding older messages
may remove information that later steps require. Tool and model integrations
add further coordination and reliability concerns, particularly when tasks run
concurrently.


           These needs motivate AgentOS as a shared runtime for multi-agent
applications. The project brings structured planning, semantic agent retrieval,
dependency-aware execution, context paging, global scheduling, resource ad-
mission, and lifecycle event reporting into one system. This provides a foun-
dation for implementing and evaluating agent workflows with visible execution
state and defined runtime policies.



1.3       PROBLEM STATEMENT


           AI applications that use multiple specialised agents lack a unified
runtime layer for coordinating their execution. In a basic request-response setup,
work is typically initiated by an individual request; developers must add their
own mechanisms to preserve state, connect tools and data sources, coordinate
agent interactions, and manage tasks that span multiple steps. These application-
specific mechanisms make it difficult to reuse infrastructure and to maintain a
consistent view of task progress.


           Without a central coordinator, the system has no common mecha-
nism to represent task dependencies, schedule ready work across concurrent
tasks, manage limited model and execution capacity, or retain relevant context
as conversations grow. Failures and delays can therefore be difficult to track
across agents, and execution behaviour is harder to inspect and evaluate. The
problem addressed by this project is how to design and implement a modular A-
gentOS runtime that coordinates heterogeneous agents through structured plans
                                                                                5


and dependency-aware execution, while managing context and shared resources
and exposing task lifecycle state to users.



1.4       OBJECTIVES


           The objectives of AgentOS are:


        1. Develop a modular AI-kernel-style runtime for specialised agents;

        2. Generate structured execution plans, retrieve suitable agents seman-
           tically, and validate their dependencies as a DAG;

        3. Manage bounded conversational context through semantic page-out
           and page-in using a vector-backed swap space;

        4. Schedule runnable work with priority aging, fairness, cooperative
           dispatch, concurrency limits, and token budgets; and

        5. Route model requests across local and cloud providers according to
           the configured hybrid-routing policy.



1.5       SCOPE


           AgentOS is implemented as a multi-agent runtime with a Next.js
frontend, a FastAPI gateway, and a Python kernel. Its services include Redis-
based event transport, MongoDB task persistence, ChromaDB retrieval, struc-
tured plan generation, dependency validation and DAG visualisation, semantic
context paging, and a global in-process scheduler with resource admission. The
runtime also supports hybrid routing across local and cloud model providers
and provides a registry of specialised agents for information gathering, research,
document handling, communication, calculation, and bounded execution tasks.
                                                                                 6


           The implemented scope does not include complete role-based access
control, distributed scheduler workers, forced termination of active language-
model calls, or automatic restoration of interrupted coroutines. These capabili-
ties remain potential areas for future development.



1.6       CONTRIBUTIONS


           This work delivers a unified runtime for coordinating heterogeneous
agents through structured plans and dependency-aware execution. Its contribu-
tions include a visual representation of task plans, a Redis-mediated stream of
lifecycle activity, semantic context page-out and retrieval, and a priority-aging
scheduler that applies concurrency and token-budget limits. The system also
provides bounded execution and recovery mechanisms for specialised agents, a-
long with configurable routing between local and cloud model providers. These
features are implemented and evaluated within the scope described in this report.



1.7       REPORT ORGANIZATION


           Chapter 2 reviews related work on autonomous agents, memory,
planning, scheduling, tool use, security, event transport, and vector retrieval.
Chapter 3 presents the AgentOS architecture and data flows, while Chapter 4
describes its algorithms, storage, events, and verification evidence. Chapter 5
reports the evaluation protocol and results for context paging, planner tool selec-
tion, and agent scheduling. The conclusion synthesises the findings and future
work; the appendix documents the registered agents and internal workflows.

                                CHAPTER 2

                        LITERATURE SURVEY


2.1       AGENTOS AND AUTONOMOUS AGENT RUNTIMES


           This chapter reviews research and technical work relevant to Agen-
tOS, including agent operating-system architectures and surveys of autonomous
agents [1, 2], multi-agent orchestration [4], and graph-based workflow execu-
tion [5]. It also examines work on memory, planning, scheduling, security, and
event-driven infrastructure. Each topic is discussed in terms of its contribution,
its limitations in relation to this project, and how AgentOS applies or extends
the underlying ideas.


2.2       AGENT RUNTIMES AND AUTONOMOUS AGENTS


           AIOS frames an LLM agent operating system around schedul-
ing, context management, memory, storage, access control, and tool manage-
ment [1]. Its operating-system analogy directly motivates the AgentOS k-
ernel, although the current AgentOS implementation is smaller and uses a
Python/Redis/MongoDB stack rather than a complete OS abstraction. The
broader survey by Wang et al. classifies LLM-based agents by construction,
applications, and evaluation [2]; it identifies coordination and reliability as open
challenges that AgentOS addresses through explicit events and DAG dependen-
cies.


           The operating-system model for LLM-based agents treats models as
system resources and agents as applications [3]. AutoGen explores configurable
multi-agent conversations, including workflows with human participation [4],
                                                                               8


while LangGraph supports graph-based orchestration and persistent workflow
state [5]. Together, these efforts show the value of representing agent coor-
dination and state explicitly. AgentOS builds on this direction by combining
dependency-aware execution with a global priority-aging scheduler and token-
budget admission.


           AgentBench provides a complementary evaluation perspective by
testing language models as agents in eight interactive environments rather than
treating generation quality as the only outcome [6]. Its multi-turn, open-ended
tasks expose failures in long-horizon reasoning, decision making, and instruc-
tion following. This distinction is important for AgentOS: a plan may be syn-
tactically valid while the resulting tool calls, dependencies, or execution state
are still incorrect. AgentOS therefore evaluates planning and runtime behaviour
separately instead of presenting a single language-generation score as evidence
of system reliability.



2.3        MEMORY AND CONTEXT MANAGEMENT


           MemGPT introduces virtual context management that moves infor-
mation between active context and external storage [7]. MemoryOS organises
memory into short-, mid-, and long-term layers and evaluates memory retention
for conversational agents [8]. These works motivate AgentOS context page-out
and page-in. AgentOS uses semantic embeddings in ChromaDB and an active-
window policy; it currently provides a project-level paging mechanism rather
than a learned memory hierarchy or an independently benchmarked memory
score.


           Recent evaluation work also shows why memory retrieval should not
be reduced to isolated fact lookup. LongMemEval measures information ex-
traction, multi-session reasoning, temporal reasoning, knowledge updates, and
                                                                                 9


abstention in long-term interactive conversations [9]. These dimensions expose
failure modes that a single retrieval-recall value can hide, particularly when pre-
viously stored information becomes outdated or when the correct response is
to abstain. The present AgentOS evaluation is deliberately narrower: it mea-
sures evidence visibility and retrieval metrics for the paging mechanism, while
answer-level judging and dynamic knowledge-update evaluation remain outside
the current scope.


           Retrieval-Augmented Generation (RAG) combines generation with a
non-parametric knowledge store [10]. ChromaDB documents collections, em-
beddings, and distance-based retrieval [11]. AgentOS uses this pattern both for
agent capability retrieval and for swapped context. The limitation is that re-
trieval quality depends on the embedding model and distance configuration; the
current implementation exposes similarity metadata but does not claim domain-
wide retrieval benchmarks.


           Evaluation frameworks such as RAGAs and ARES distinguish the
quality of retrieved context from the quality of the generated answer. RAGAs
provides reference-free measures for retrieval relevance, faithfulness, and an-
swer quality [12]. ARES evaluates context relevance, answer faithfulness, and
answer relevance, and uses synthetic training data with a small human-annotated
set for calibration [13]. These frameworks suggest ways to extend AgentOS e-
valuation. The current context-paging experiments measure evidence visibility
and retrieval performance; future work could also assess whether retrieved con-
text supports faithful and relevant answers.



2.4       PLANNING, TOOL USE, AND REFLECTION


           ReAct interleaves reasoning and action so that an agent can use ex-
ternal tools during problem solving [14]. Toolformer studies self-supervised
                                                                             10


learning for deciding when and how to call APIs [15]. Generative Agents com-
bine memory, reflection, and planning for believable behaviour [16]. Reflexion
uses verbal feedback to improve subsequent attempts without updating mod-
el weights [17]. AgentOS adopts structured planning, explicit tool boundaries,
persisted events, and bounded self-healing, but does not train models or claim
the autonomous reflection capabilities of these research systems.


           ToolLLM and its ToolBench dataset study tool use at a substantially
larger scale, covering more than 16,000 real-world REST APIs across 49 cate-
gories and evaluating both API recommendation and multi-step call paths [18].
This work highlights that tool use depends on capability retrieval, argument
construction, and execution-path selection, not only on the model’s general rea-
soning ability. AgentOS addresses the same separation at a smaller system level
through a registered agent catalogue, semantic candidate retrieval, structured
plans, and an end-to-end tool-selection evaluation. The comparison is concep-
tual rather than numerical: AgentOS does not claim ToolBench-scale coverage
or model-training results.


           Recent survey work provides a useful vocabulary for positioning this
architecture within workflow-optimisation research. Yue et al. distinguish stat-
ic workflow templates from dynamic runtime graphs and separate reusable de-
signs, run-specific realised graphs, and execution traces [19]. They also argue
that workflow evaluation should consider graph structure, execution cost, ro-
bustness, and variation across inputs in addition to downstream task metrics.
This perspective supports AgentOS’s separation of planning, DAG validation,
scheduling, and runtime evidence, while also identifying graph-level optimisa-
tion and cost-aware evaluation as directions for future work.


           The Transformer architecture introduced an attention-based ap-
proach that underlies many modern large language models [20]. Because these
                                                                              11


models process inputs within finite context windows, AgentOS provides exter-
nal context management to preserve and retrieve task information across execu-
tion steps. The language model itself remains an external provider selected by
the planner and runtime.



2.5       SCHEDULING, RESOURCES, AND RELIABILITY


           Classical operating-system scheduling shows why priority alone can
starve old work and why aging can improve fairness [21]. Linux cgroups pro-
vide a practical model for resource accounting and isolation [22]. AgentOS
adapts these ideas to agent work: effective priority increases with queue wait,
admission checks global and per-task slots, and token reservations are tracked
before dispatch. Unlike a CPU scheduler, AgentOS cannot forcibly preempt
an in-flight remote LLM request; its dispatch quantum is cooperative, with full
execution checkpoints remaining a future extension.


           The workflow and orchestration literature emphasises explicit depen-
dency graphs and stateful execution. LangGraph persistence documents check-
pointed graph state [23], while Temporal documents durable workflow execu-
tion [24]. AgentOS currently validates and executes a DAG in-process and
persists task/event evidence; automatic continuation of interrupted coroutines
remains future work.



2.6       SECURITY AND SANDBOXED EXECUTION


           The Model Context Protocol specifies a standard way for AI appli-
cations to connect models with tools and data sources [25]. OWASP’s LLM
security guidance highlights risks including excessive agency, insecure tool use,
and code execution [26]. Python subprocess execution and filesystem scoping
                                                                                 12


are therefore bounded in the code runner. Firecracker demonstrates the stronger
isolation achievable with microVMs [27]. AgentOS’s current runner limits du-
ration and output and scopes its working directory, but it is not a substitute for a
hardened kernel or microVM sandbox.



2.7       EVENT-DRIVEN INFRASTRUCTURE


           Redis documents Pub/Sub as a low-latency message distribution
mechanism [28]. MongoDB provides durable document storage suitable for
task history and metadata [29]. AgentOS uses Redis for transient task/event
transport and queue metadata and MongoDB for durable task records. Redis
Pub/Sub alone is not a durable event log; recovery therefore persists relevant
state in Redis hashes and MongoDB events, with full replay and exactly-once
semantics left for future work.



2.8       RESEARCH GAP AND POSITIONING


           The reviewed systems provide strong solutions for individual con-
cerns: planning, memory, graph orchestration, tool use, security, or workflow
durability. AgentOS’s contribution is an integrated educational/runtime proto-
type that makes these concerns observable together in one project. Its distinctive
implementation choices are semantic agent selection, explicit DAG validation,

3.1        DESIGN PRINCIPLES


           AgentOS is designed as a modular runtime. The gateway handles
external requests, the orchestrator converts a prompt into a structured plan, and
the kernel owns execution concerns. Redis is used for low-latency coordination
and event transport, while MongoDB stores task history. ChromaDB stores em-
beddings used for semantic agent retrieval and context swap. The design keeps
the current dependency truth in the DAG executor and treats scheduler decisions
as admission and dispatch decisions.



3.2        OVERALL ARCHITECTURE


           Figure 3.1 presents AgentOS as a set of cooperating modules that
manage task submission, planning, execution, and feedback. The main modules
and their responsibilities are:


        1. User interface: The Next.js frontend accepts task requests and dis-
           plays plans, execution status, and activity updates.

        2. API gateway: The FastAPI backend accepts requests from the fron-
           tend, creates or retrieves task state, and passes work to the kernel.

        3. Planner and agent selection: The planner creates structured task
           steps and retrieves suitable specialised agents from the registry.
                                                                               14


        4. Kernel and DAG executor: The Python kernel validates step depen-
           dencies and executes each step when its prerequisites are complete.

        5. Scheduler and resource manager: The global scheduler dispatches
           ready work across tasks, while resource admission applies concur-
           rency and token-budget limits.

        6. Context management: The context pager stores older task messages
           in ChromaDB and retrieves relevant content when later steps need it.

        7. Agent and tool execution: Registered agents perform specialised
           work using available tools; the bounded code runner supports con-
           trolled Python execution. A complete permission store and MCP-
           compatible tool manager remain proposed extensions.

        8. Model reasoning and routing: A shared model interface routes re-
           quests to configured local or cloud providers according to the hybrid
           routing policy.

        9. Persistence and event communication: MongoDB stores task
           records, while Redis supports coordination and event transport to the
           frontend.


In a typical workflow, the user submits a task through the frontend, and the gate-
way forwards it to the kernel. The planner prepares a structured plan and selects
agents. The kernel validates the plan, schedules eligible steps, and coordinates
their execution. During this process, the runtime manages context and model
routing, records task state, and publishes events that the frontend uses to show
progress. The figure includes both implemented components and proposed ex-

3.3          HYBRID LLM REASONING ENGINE


             AgentOS uses a privacy-aware hybrid reasoning engine to balance
cloud-model capability with local data protection. The model factory exposes
one LangChain-compatible facade to the planner, agents, and response gener-
ator, while the facade selects a provider for each invocation. Groq is used for
non-sensitive orchestration work when a cloud credential is configured; Olla-
ma is used for privacy-sensitive work such as local file inspection, repository or
code analysis, academic material, personal information, credentials, and other
locally scoped data. The local path is configured with an Ollama model such as
llama3.2 or qwen3:8b and communicates with the host-local Ollama service.


             The model router applies conservative input classification before a
model call. It extracts text from strings, message lists, and structured inputs,
then checks privacy and local-resource indicators. A sensitive classification has
precedence over cloud routing, so the request remains local even when Groq is
available. The router also supports explicit local, cloud, and hybrid modes.
In hybrid mode, an unavailable or failed Groq request is retried through Ollama,
providing a local continuity path. This design makes the provider choice a ker-
nel concern rather than a frontend concern: the UI reports the decision emitted
by the kernel instead of attempting to infer privacy from the prompt.


             The shared model interface also supports structured outputs and tool
binding. Consequently, planning, agent tool calls, and final response generation
can all use the routing policy without requiring separate graph implementation-
s. Each selected route produces an llm.ROUTED event containing the provider,
sensitivity flag, reason, and operation. These events are persisted with the task
and forwarded to the frontend, making the privacy boundary auditable during
execution.

3.5       PLANNER AND DAG EXECUTION


           The planner retrieves relevant agent descriptions, requests a struc-
tured execution plan, and applies a fallback plan when the provider is unavail-
able. Each step includes an identifier, agent name, description, and dependency
list. The validator canonicalises identifiers, rejects unknown dependencies and
cycles, and supplies a sequential fallback only when a plan omits dependen-
cies. The executor runs only steps whose prerequisites are complete. Figure 3.3
summarises this path. The frontend uses the same validated plan to generate
Mermaid source and draw the plan graph, ensuring that displayed edges repre-
sent dependencies rather than decorative links.


           The planning boundary separates model output from executable run-
time state. Candidate agents are first retrieved from their capability description-
s, after which the planner normalises the response into a bounded step schema.
Missing or malformed fields are rejected before execution, and the determinis-
tic fallback preserves a valid task path when the model cannot provide a usable
plan. This separation keeps provider-specific reasoning outside the executor
and makes failures observable as planning or validation events rather than silent
execution errors.


           Once a plan passes validation, the dependency graph determines
readiness: a step enters the runnable set only after every prerequisite has com-
pleted successfully. Independent steps can therefore be considered concurrent-
ly, while dependent steps remain blocked without occupying execution capacity.
The scheduler selects from the ready set according to priority and resource pol-
icy, and each completion updates the graph before the next dispatch decision.
The same validated dependency edges are sent to the frontend, so the visual
plan and the runtime execution order describe one consistent graph.

3.8       RESOURCE MANAGEMENT


           Figure 3.6 details how resource admission is intended to connect the
scheduler, resource manager, agent runtime, and monitoring feedback. First, the
scheduler submits a resource request (1), and the manager obtains applicable
limits from the resource policy store (2). Within the manager, token accounting,
quota checks, and process monitoring provide inputs to the resource checker,
which compares the request with the available capacity. The decision engine
then selects an outcome: allow the work to proceed, throttle it until capacity is
available, or preempt work when a policy requires resources to be reclaimed.
An approval is returned to the agent runtime (3). Execution metrics flow from
the runtime to monitoring (4); monitoring summarizes usage and feeds those
measurements back to the manager (5). The resulting resource decision is re-
                                                                               22


turned to the scheduler (6), which can dispatch, defer, or otherwise handle the
job.


           The diagram represents the broader design, while the current imple-
mentation provides a narrower admission mechanism. Its in-process resource
manager checks a global limit of three active execution slots, a per-task limit of
two slots, and a configurable task token budget that defaults to 50,000 tokens. A
job waits in the scheduler queue when a slot is unavailable, and jobs that exceed
the token budget are denied and reported through lifecycle events. The separate
policy store, process monitor, and hard-preemption path shown in the figure are
design extensions; an active remote model request cannot currently be forcibly
terminated.

4.1       IMPLEMENTATION ENVIRONMENT


          The kernel is implemented in Python using asynchronous services.
The backend is FastAPI-based and the frontend is implemented with Next.js
and TypeScript. Redis provides task/event channels and scheduler metada-
ta; MongoDB stores task records and event history; ChromaDB provides per-
sistent vector collections for planning and context swap. The LLM layer is
provider-independent at the graph boundary: a hybrid model facade presents
one asynchronous LangChain interface while selecting Groq or Ollama per in-
vocation. Provider-specific LLM usage is treated as optional metadata because
some providers do not return reliable token counts.



4.2       SEMANTIC AGENT RETRIEVAL


          Agent descriptions are embedded in a persistent ChromaDB collec-
tion. A task description is used as a query, and the top candidate records are
returned with their distances and metadata. In the configured cosine space,
ChromaDB returns d = 1 − cos(θ), so the implementation reports s = 1 − d.
It does not divide by two; that transformation would be appropriate for a d-
ifferent distance normalisation. An LRU cache reduces repeated retrieval for
identical descriptions. Algorithm 4.1 summarises this candidate-retrieval and
cosine-distance conversion procedure.

4.3       PLANNER AND FALLBACK


           The planner asks the configured LLM for a structured execution plan.
The response is parsed into steps and normalised against the agent registry. If the
LLM request fails, exceeds quota, or produces invalid structure, a deterministic
fallback creates a usable plan from the best retrieved agent(s). This maintains
task execution and observability without pretending that the fallback has the
same reasoning quality as the provider.


           Figure 4.1 illustrates the complete optimised planning path, from se-
mantic candidate retrieval through structured plan validation, fallback routing,
DAG construction, scheduling, and runtime execution. It shows how a user
request is converted into executable work. The planner first embeds the task
and retrieves candidate agents whose capability descriptions are semantically
related to the request. These candidates are supplied to the language model,
which proposes structured steps with agent names, descriptions, and dependen-
cies. The runtime then normalises the response and validates the step identifiers,
selected agents, and dependency edges before constructing the execution DAG.
If the model is unavailable or returns malformed output, the fallback path s-
elects the best retrieved agent or agents and creates a deterministic sequential
plan. The validated graph is passed to the scheduler, which dispatches ready
steps and sends lifecycle updates to the runtime and frontend. Thus, the figure

the ready set. If the count is smaller than the number of steps, the dependency

graph contains a cycle and is rejected. The same validated dependency lists are

4.7       RESOURCE ADMISSION AND TOKEN BUDGETS
                                                                              32


           The resource manager checks active global slots, active slots for the
task, and the cumulative estimated token reservation for the task. A tempo-
rary denial leaves work waiting; an exhausted task budget is converted into a
blocked/failed outcome rather than leaving the task silently pending. Actual
provider usage, when available, is recorded separately from estimated admis-
sion tokens. This distinction explains why a provider such as Groq may display
zero usage metadata even while the scheduler correctly enforces its configured
estimate. Admission is performed before dispatch and released after comple-
tion, failure, or cancellation. The scheduler therefore distinguishes capacity
denial from execution failure: a job that cannot currently obtain a slot remains
visible as waiting, while a job that exceeds its token budget is rejected accord-
ing to policy. Global and per-task counters are updated together so that one task
cannot consume all available capacity, and the recorded reservation is carried
into lifecycle events for later analysis. These checks provide a simple admission
boundary between planning and execution while keeping the policy observable
and configurable.

                               CHAPTER 5

      RESULTS AND PERFORMANCE ANALYSIS


           This chapter reports the evaluation of three AgentOS subsystems: the
context-paging engine, the model-backed planner, and the global agent sched-
uler. The results are presented in a consistent order. First, the reporting proto-
col defines the datasets, comparison conditions, and metrics. The chapter then
evaluates context paging, planner tool selection, and scheduler behaviour in se-
quence. The final section consolidates the findings and states the limitations of
the measurements.



5.1       REPORTING PROTOCOL


           The evaluations use fixed task or question sets, documented config-
urations, and reproducible scoring rules. For each experiment, the expected
evidence, tool set, or scheduler outcome was defined before the trial. Raw trial
records were retained so that aggregate values could be recomputed. Percent-
ages are pooled over the reported trials; latency values are reported using the
aggregate statistic available for each run, with percentile values used for queue-
ing measurements.


           The context-paging experiments use deterministic synthetic conver-
sations and a fixed pilot subset of the LoCoMo long-term conversational-
memory dataset and benchmark [30]. The planner experiment uses the Agen-
tOS function catalogue and a fixed 50-trial task-selection run. The scheduler
experiment uses deterministic smoke scenarios and seeded synthetic workloads.
These are project-level implementation and reliability evaluations, not claims of
production capacity or general performance.
                                                                              44


5.2       CONTEXT-PAGING ENGINE


           The context engine was evaluated using two complementary dataset-
s. The first is a deterministic synthetic smoke set designed to verify the paging
pipeline, telemetry, and comparison harness. The second is a pilot evaluation
derived from the LoCoMo benchmark. The configurations compare complete-
context access, recent-message truncation, vector retrieval, and AgentOS pag-
ing.


           The results are retrieval-oriented. A successful retrieval trial mean-
s that the annotated evidence required to answer the question is visible in the
active context or is returned by the paging operation. This measure is intention-
ally separate from end-to-end language-model answer accuracy, which requires
a fixed answer model and judge and was not enabled for these runs.



5.2.1     Evaluation protocol


           All configurations used the same local ChromaDB embedding func-
tion, active context window, question text, conversation history, and candidate
budget within each dataset. The full-context configuration is a quality control:
it receives the complete conversation and therefore does not perform retrieval.
Recent truncation retains only the active window. Vector RAG performs direct
semantic retrieval, while AgentOS paging combines a larger semantic candi-
date pool with one-message neighbourhood expansion and a lightweight lexical
reranking stage.


           The synthetic run expanded five seed scenarios into a fixed local
smoke set and executed 400 configuration trials. The external run used a fixed
pilot subset of the official LoCoMo questions and executed 800 configuration
trials. The threshold sweep was retained as a sensitivity analysis rather than as
                                                                                    45


evidence that a threshold was universally optimal. Page-in and page-out laten-
cies, embedding-cache behaviour, token estimates, and raw trial records were
recorded for every configuration.

5.5       INTEGRATED INTERPRETATION


           The context engine demonstrates measurable active-context reduc-
tion and improved retrieval over direct vector RAG on the LoCoMo pilot, al-
though the synthetic smoke set remains easier than the external conversation-
al data. The planner achieves 76.0% end-to-end exact tool-set accuracy and
required-tool recall across 50 trials; its main failure mode is missing required
                                                                             56


tool calls rather than provider unavailability. The scheduler preserves through-
put while substantially reducing high-priority queue waiting under contention.


           These results have important limitations. The context experiments
use a deterministic synthetic set and a fixed LoCoMo pilot rather than the
complete benchmark; threshold selection is exploratory, and no answer-model
judging or confidence intervals were enabled. The planner evaluation uses an
AgentOS-specific task set and should not be generalized beyond that scope. The
scheduler benchmark uses deterministic service times and stubbed persistence,
so it is not a production-capacity claim. Accordingly, the findings establish
implementation behaviour under the stated conditions, not universal superi-
ority over alternative systems. Future work should evaluate held-out planner
tasks and thresholds, add answer judging, replace stubbed persistence, and use
production-like scheduler traces.

                                CHAPTER 6

              CONCLUSION AND FUTURE WORK


              AgentOS demonstrates that planning, dependency-aware execution,
context paging, scheduling, resource admission, bounded code execution, mod-
el routing, and frontend observability can be integrated into one multi-agent
runtime. The implemented architecture connects the frontend, gateway, Python
kernel, data stores, event transport, specialised agents, and model providers into
a single execution pipeline. By separating planning, validation, scheduling, and
runtime execution, the system makes agent workflows explicit, reusable, and
observable rather than leaving coordination logic scattered across individual ap-
plications.


              The evaluation provides evidence that these design choices are use-
ful within the defined study conditions. Context retrieval achieved 98.0% suc-
cess on the synthetic set and 35.0% on the LoCoMo pilot, planner evaluation
achieved a 76.0% exact tool-set rate across 50 trials, and priority aging reduced
high-priority queue-wait P95 by approximately 68% in steady state and 78% un-
der contention compared with FIFO. Together, these results support AgentOS
as a practical and transparent prototype for coordinating multi-step agent tasks,
while the dataset scope, provider conditions, and controlled benchmark design
limit broader generalisation.


              Future work will extend AgentOS beyond its current prototype
boundaries by improving durable recovery, execution checkpoints, and restora-
tion of interrupted coroutines. It will also add explicit permission policies,
stronger sandbox isolation, and more complete hybrid local/cloud model rout-
ing. Further evaluation should use production-like traces, non-stubbed persis-
                                                                               58


tence, varied provider conditions, held-out conversations, paraphrased tasks,
answer-level judging, and larger repeated trials. Additional tool-use scenarios
and event-triggered workflows can provide a broader assessment of the archi-
tecture’s generalisability and practical readiness.
