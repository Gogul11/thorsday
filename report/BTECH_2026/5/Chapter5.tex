\chapter{\uppercase{Results and Performance Analysis}}
\label{chap5}

This chapter reports the evaluation of three AgentOS subsystems: the context-paging engine, the model-backed planner, and the global agent scheduler. The results are presented in a consistent order. First, the reporting protocol defines the datasets, comparison conditions, and metrics. The chapter then evaluates context paging, planner tool selection, and scheduler behaviour in sequence. The final section consolidates the findings and states the limitations of the measurements.

\section{\uppercase{Reporting protocol}}

The evaluations use fixed task or question sets, documented configurations, and reproducible scoring rules. For each experiment, the expected evidence, tool set, or scheduler outcome was defined before the trial. Raw trial records were retained so that aggregate values could be recomputed. Percentages are pooled over the reported trials; latency values are reported using the aggregate statistic available for each run, with percentile values used for queueing measurements.

The context-paging experiments use deterministic synthetic conversations and a fixed pilot subset of the LoCoMo long-term conversational-memory dataset and benchmark~\cite{locomo2024}. The planner experiment uses the AgentOS function catalogue and a fixed 50-trial task-selection run. The scheduler experiment uses deterministic smoke scenarios and seeded synthetic workloads. These are project-level implementation and reliability evaluations, not claims of production capacity or general performance.

\section{\uppercase{Context-paging engine}}

The context engine was evaluated using two complementary datasets. The first is a deterministic synthetic smoke set designed to verify the paging pipeline, telemetry, and comparison harness. The second is a pilot evaluation derived from the LoCoMo benchmark. The configurations compare complete-context access, recent-message truncation, vector retrieval, and AgentOS paging.

The results are retrieval-oriented. A successful retrieval trial means that the annotated evidence required to answer the question is visible in the active context or is returned by the paging operation. This measure is intentionally separate from end-to-end language-model answer accuracy, which requires a fixed answer model and judge and was not enabled for these runs.

\subsection{Evaluation protocol}

All configurations used the same local ChromaDB embedding function, active context window, question text, conversation history, and candidate budget within each dataset. The full-context configuration is a quality control: it receives the complete conversation and therefore does not perform retrieval. Recent truncation retains only the active window. Vector RAG performs direct semantic retrieval, while AgentOS paging combines a larger semantic candidate pool with one-message neighbourhood expansion and a lightweight lexical reranking stage.

The synthetic run expanded five seed scenarios into a fixed local smoke set and executed 400 configuration trials. The external run used a fixed pilot subset of the official LoCoMo questions and executed 800 configuration trials. The threshold sweep was retained as a sensitivity analysis rather than as evidence that a threshold was universally optimal. Page-in and page-out latencies, embedding-cache behaviour, token estimates, and raw trial records were recorded for every configuration.

\section{\uppercase{Planner and tool selection}}

The planner evaluation measures whether the model selects the registered AgentOS functions required by a task. The model endpoint was Groq using \texttt{openai/gpt-oss-120b}. Each registered agent was exposed as an OpenAI-compatible function. The same catalogue and routing prompt were used for every trial, and required tool-call mode was enabled because every task required at least one registered agent.

Exact tool-set accuracy is the fraction of trials for which the selected agent functions exactly matched the expected set. Required-tool recall is the fraction of trials in which every expected function was selected. The end-to-end measures count a failed model tool call as an incorrect outcome. Provider errors and model tool-call failures are recorded separately.

Table~\ref{tab:planner-tool-results} summarises the 50-trial run. Thirty-eight trials produced the expected tool set, while twelve trials failed at the tool-call stage. No provider errors were recorded. The aggregate latency, computed from category-level means weighted by trial count, was 1003.36 ms.

\section{\uppercase{Agent scheduler}}
\label{sec:agent-scheduler-evaluation}

The scheduler evaluation consists of a deterministic smoke suite and a controlled workload benchmark. The smoke suite executed 21 trials covering concurrency and task limits, cooperative preemption, cumulative token budgets, oversized jobs, priority ordering, quota retry, and runner failure; all 21 completed successfully.

The workload benchmark compared the implemented priority-aging policy with an admission-aware FIFO policy using the same seeded workloads, service-time distributions, and priority values. Each policy and workload profile was repeated ten times, producing 40 trials in total. Persistence was stubbed, so the measurements capture in-process scheduling and asynchronous runner behaviour rather than Redis or MongoDB network overhead. To preserve readability, the results are separated by workload profile: steady-state results are reported in Table~\ref{tab:scheduler-steady-state}, and queue-contention results are reported in Table~\ref{tab:scheduler-contention}.

Priority aging reduced high-priority queue-wait $P_{95}$ by 140.82 ms in steady state and by 358.14 ms under contention, corresponding to approximate reductions of 68\% and 78\% relative to FIFO. Throughput remained effectively unchanged under contention (+0.10\%) and decreased by 1.45\% in steady state. Overall queue-wait $P_{95}$ increased by approximately 3.6 ms in both profiles because the policy protects urgent work by allowing lower-priority jobs to wait longer. No concurrency-limit violations or cross-task completion imbalance were observed. These measurements should be interpreted as a controlled same-host comparison, not as a production-capacity claim.

\section{\uppercase{Integrated interpretation and limitations}}

The context engine demonstrates measurable active-context reduction and improved retrieval over direct vector RAG on the LoCoMo pilot, although the synthetic smoke set remains easier than the external conversational data. The planner achieves 76.0\% end-to-end exact tool-set accuracy and required-tool recall across 50 trials; its main failure mode is missing required tool calls rather than provider unavailability. The scheduler preserves throughput while substantially reducing high-priority queue waiting under contention.

These results have important limitations. The context experiments use a deterministic synthetic set and a fixed LoCoMo pilot rather than the complete benchmark; threshold selection is exploratory, and no answer-model judging or confidence intervals were enabled. The planner evaluation uses an AgentOS-specific task set and should not be generalized beyond that scope. The scheduler benchmark uses deterministic service times and stubbed persistence, so it is not a production-capacity claim. Accordingly, the findings establish implementation behaviour under the stated conditions, not universal superiority over alternative systems. Future work should evaluate held-out planner tasks and thresholds, add answer judging, replace stubbed persistence, and use production-like scheduler traces.
