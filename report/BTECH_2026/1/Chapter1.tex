\section{\uppercase{From Operating Systems to AgentOS}}
Operating systems coordinate applications by managing processing, memory, storage, and access to shared resources~\cite{silberschatz2018os}. AI agents likewise need a runtime that can select tools, execute multi-step plans, preserve relevant context, and coordinate specialised agents. Existing research explores agent runtimes and multi-agent orchestration, while identifying reliability, planning, and memory management as ongoing challenges~\cite{wang2024survey,wu2023autogen}. These needs motivate applying selected operating-system principles to agent workflows~\cite{mei2024aios,packer2023memgpt}.

This project develops AgentOS, a shared runtime that turns a user's task into a structured plan, selects specialised agents, validates dependencies, and schedules ready work. Its Python kernel connects a Next.js interface and FastAPI gateway with Redis coordination and events, MongoDB task history, ChromaDB retrieval, context paging, resource admission, and hybrid local/cloud model routing. The system makes multi-agent execution observable through lifecycle events and task state, while addressing the distinct constraints of model-based work, including limited context, variable execution time, and provider failures~\cite{wu2024longmemeval}. 

\section{\uppercase{Motivation}}
AI applications are moving from single-turn assistants toward agents that can plan, use tools, retain task context, and carry out work across multiple steps. As these applications become more capable, their infrastructure needs grow: developers must manage task state, choose suitable agents, coordinate dependent and independent work, control access to shared resources, and handle failures. When each application implements these mechanisms separately, the resulting integrations can be difficult to reuse, extend, and inspect.

The request-response model alone is also a poor fit for work that must continue across steps or involve several agents. Agent workflows need explicit lifecycle and dependency management so that work can be scheduled as it becomes ready and its progress can be observed. They also need a deliberate context strategy: model context is limited, but simply discarding older messages may remove information that later steps require. Tool and model integrations add further coordination and reliability concerns, particularly when tasks run concurrently.

These needs motivate AgentOS as a shared runtime for multi-agent applications. The project brings structured planning, semantic agent retrieval, dependency-aware execution, context paging, global scheduling, resource admission, and lifecycle event reporting into one system. This provides a foundation for implementing and evaluating agent workflows with visible execution state and defined runtime policies.

\section{\uppercase{Problem Statement}}
AI applications that use multiple specialised agents lack a unified runtime layer for coordinating their execution. In a basic request-response setup, work is typically initiated by an individual request; developers must add their own mechanisms to preserve state, connect tools and data sources, coordinate agent interactions, and manage tasks that span multiple steps. These application-specific mechanisms make it difficult to reuse infrastructure and to maintain a consistent view of task progress.

Without a central coordinator, the system has no common mechanism to represent task dependencies, schedule ready work across concurrent tasks, manage limited model and execution capacity, or retain relevant context as conversations grow. Failures and delays can therefore be difficult to track across agents, and execution behaviour is harder to inspect and evaluate. The problem addressed by this project is how to design and implement a modular AgentOS runtime that coordinates heterogeneous agents through structured plans and dependency-aware execution, while managing context and shared resources and exposing task lifecycle state to users.

\section{\uppercase{Objectives}}
The objectives of AgentOS are:
\begin{enumerate}
\item Develop a modular AI-kernel-style runtime for specialised agents;
\item Generate structured execution plans, retrieve suitable agents semantically, and validate their dependencies as a DAG;
\item Manage bounded conversational context through semantic page-out and page-in using a vector-backed swap space;
\item Schedule runnable work with priority aging, fairness, cooperative dispatch, concurrency limits, and token budgets; and
\item Route model requests across local and cloud providers according to the configured hybrid-routing policy.
\end{enumerate}

\section{\uppercase{Scope}}
AgentOS is implemented as a multi-agent runtime with a Next.js frontend, a FastAPI gateway, and a Python kernel. Its services include Redis-based event transport, MongoDB task persistence, ChromaDB retrieval, structured plan generation, dependency validation and DAG visualisation, semantic context paging, and a global in-process scheduler with resource admission. The runtime also supports hybrid routing across local and cloud model providers and provides a registry of specialised agents for information gathering, research, document handling, communication, calculation, and bounded execution tasks.

The implemented scope does not include complete role-based access control, distributed scheduler workers, forced termination of active language-model calls, or automatic restoration of interrupted coroutines. These capabilities remain potential areas for future development.

\section{\uppercase{Contributions}}
This work delivers a unified runtime for coordinating heterogeneous agents through structured plans and dependency-aware execution. Its contributions include a visual representation of task plans, a Redis-mediated stream of lifecycle activity, semantic context page-out and retrieval, and a priority-aging scheduler that applies concurrency and token-budget limits. The system also provides bounded execution and recovery mechanisms for specialised agents, along with configurable routing between local and cloud model providers. These features are implemented and evaluated within the scope described in this report.
