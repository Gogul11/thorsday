\section{\uppercase{Background}}
Operating systems form the shared software foundation between computer hardware and the applications that use it. A conventional operating system manages processor time, memory, files, input/output devices, and the execution of processes. It offers applications stable abstractions and common services, allowing each program to focus on its own purpose instead of implementing low-level resource management. The operating system also coordinates competing work: it decides which process can use a processor, allocates memory, maintains files, and enforces boundaries between processes. These responsibilities make it possible for many applications to run on the same computer in a controlled and observable manner~\cite{silberschatz2018os}.

Artificial intelligence applications are beginning to move beyond the conventional chatbot model. A reactive chatbot generally receives a prompt and generates a response, while a language-model-based agent can be given a goal, decide what information or action is needed, call tools, inspect the result, and continue through several steps. Agents can also retain or retrieve task-related information and use feedback from their environment to revise a plan. Research surveys describe a growing range of agent designs and applications, while also identifying reliability, planning, memory, and evaluation as continuing challenges~\cite{wang2024survey}. This change expands the role of an AI application: it may act as a digital worker that carries out part of a user's task, rather than only returning text about it.

More involved tasks can be divided among specialised agents. For example, one agent may gather information, another may analyse a document, and another may prepare or check the final result. Multi-agent frameworks demonstrate how agents can be connected through conversation, tool use, and human input~\cite{wu2023autogen}. This division of work can make a system more modular, but it also introduces coordination requirements. The application must decide which agents are suitable, define what each step depends on, determine which steps can run independently, and combine their outputs. A failure or delay in one step can affect later steps, so task status and execution decisions must be tracked across the whole workflow.

The coordination burden grows when agents share limited resources. Language-model calls consume time, tokens, and sometimes paid provider capacity. Each model also has a finite context window, so a long-running task cannot always retain its full history in every request. Concurrent tasks may compete for model access, execution slots, memory, and tool services. The runtime must therefore control which work is ready, manage access to resources, preserve useful context, and report why an action succeeded, failed, waited, or was retried. Tool execution also creates security and reliability concerns: an agent may request an unsuitable operation, produce invalid structured output, or return an error that must be handled without losing the task's state. When every application implements these mechanisms independently, infrastructure is duplicated and behaviour becomes difficult to compare or inspect.

Context management is especially important because an agent's current prompt is only a limited working view of a task. Keeping every earlier message can exceed the model's context limit and increase inference cost, while deleting old messages solely by age can remove decisions, constraints, or evidence that later steps need. A runtime therefore needs a deliberate way to retain task history and retrieve relevant information when it becomes useful again. Research on long-term conversational memory highlights that successful memory use depends on retrieving the right evidence for a later query, not simply storing a large volume of text~\cite{packer2023memgpt,wu2024longmemeval}. In a multi-agent workflow, this challenge also crosses agent boundaries: a result produced by one agent may become necessary context for another, and the runtime must preserve its task association and provenance.

The runtime also needs to make execution understandable to people. A final answer alone does not reveal which agents were selected, which steps are waiting on dependencies, whether a tool call failed, or how much capacity remains. Structured lifecycle events and task records can expose these changes without requiring users to infer system state from incomplete text responses. This observability supports diagnosis and evaluation: developers can compare planned work with executed work, identify where time or resources were spent, and distinguish a model failure from a scheduling or tool failure. It also provides a basis for applying consistent policies to tool access and execution limits across different applications.

These challenges suggest an operating-system-inspired foundation for AI agents. In this analogy, agents and their tasks resemble applications and processes; plans describe work and dependencies; scheduling selects executable tasks; and context services manage information needed by later model calls. Resource-management services can apply limits to concurrency and token budgets, while event mechanisms make state changes visible to users and other components. Early research has explored this direction directly. AIOS frames an operating system for LLM agents around concerns such as scheduling, memory, storage, and tool management~\cite{mei2024aios}. MemGPT similarly uses operating-system ideas to manage information across a limited context window~\cite{packer2023memgpt}. These works establish the relevance of the analogy, but an AI runtime must account for properties that differ from ordinary processes: model behaviour is probabilistic, calls may be remote and slow, and provider usage or failure information may be incomplete.

An Agent Operating System, or AgentOS, applies these ideas as a runtime layer for planning and coordinating AI agents. Its purpose is to provide shared services around the agents: task representation, agent selection, dependency validation, scheduling, context management, resource admission, and execution-state reporting. This is not a claim that an AI runtime replaces a conventional operating system. Rather, it adapts selected operating-system principles to the needs of applications that rely on language models, tools, and multiple cooperating agents. A common runtime can make the workflow explicit and provide one place to observe how a task progresses, while leaving application-specific goals and agent capabilities to the applications built on it.

This project develops and evaluates such a runtime through AgentOS. A user submits a task through a web interface; the planning layer converts it into steps and selects specialised agents; and the kernel validates dependencies and schedules ready work. The system combines semantic agent retrieval, dependency-aware graph execution, context paging, concurrency and token-budget admission, and lifecycle events that can be shown to the user. Its implementation connects a Next.js frontend, a FastAPI gateway, a Python kernel, Redis coordination and event transport, MongoDB task persistence, and ChromaDB vector retrieval. Hybrid model routing supports local and cloud providers according to the configured policy. Together, these components turn the operating-system analogy into a concrete project: a reusable and observable runtime for applications in which agents plan, use tools, and cooperate on multi-step tasks.

\section{\uppercase{Motivation}}
In a conventional chatbot, application logic, conversation state, tool invocation, and error handling are often tightly coupled. This makes it difficult to run independent work concurrently or to explain why an agent was selected. Long conversations also exceed the practical context window of a model, while blindly truncating history can remove information needed by later steps. Finally, unrestricted execution services and tools create safety and observability risks.

AgentOS is motivated by the need for a reusable runtime layer. The project investigates how planning, agent retrieval, DAG execution, semantic context paging, global scheduling, resource accounting, event streaming, and sandboxed execution can be composed into one observable system.

\section{\uppercase{Problem Statement}}
There is no single lightweight runtime in the project environment that coordinates heterogeneous agents across multiple concurrent tasks while enforcing dependencies, observing token and concurrency budgets, preserving relevant context, and exposing execution state to a user interface. Reimplementing these facilities inside each application increases duplication, makes failures difficult to diagnose, and prevents systematic evaluation of scheduling and resource policies.

\section{\uppercase{Objectives}}
The objectives of AgentOS are:
\begin{enumerate}
\item Develop a modular AI-kernel-style runtime for specialised agents;
\item Generate structured execution plans, retrieve suitable agents semantically, and validate their dependencies as a DAG;
\item Manage bounded conversational context through semantic page-out and page-in using a vector-backed swap space;
\item Schedule runnable work with priority aging, fairness, cooperative dispatch, concurrency limits, and token budgets; and
\item Execute agent tasks reliably while publishing lifecycle events and measurable activity to the user interface.
\end{enumerate}

\section{\uppercase{Scope}}
The current phase covers a Next.js frontend, FastAPI gateway, Python kernel, Redis event transport, MongoDB task persistence, ChromaDB retrieval, structured planning, DAG validation and Mermaid generation, context paging, a global in-process scheduler, resource admission, hybrid local/cloud model routing, and a registry of specialised agents for information, research, documents, communication, calculation, and bounded execution tasks. The scope does not claim complete RBAC, distributed scheduler workers, forced termination of active LLM calls, or automatic coroutine restoration. These are documented as future work.

\section{\uppercase{Contributions}}
The project contributions are a unified execution model for heterogeneous agents, a visible plan graph, a Redis-mediated activity stream, a semantic context paging mechanism, a priority-aging scheduler with resource admission, and a bounded execution and recovery path for specialised agents. The implementation also makes a deliberate distinction between design aspirations and features that are present and testable in the repository.
