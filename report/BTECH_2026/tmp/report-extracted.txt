ABSTRACT

Large-language-model applications are evolving from single-turn
chat interfaces into systems that plan, use tools, preserve context, and coordinate
multiple specialised agents.

However, application developers commonly

rebuild scheduling, memory, event propagation, execution monitoring, and
failure handling for each project. This report presents AgentOS, a hybrid
multi-agent runtime environment that provides these operating-system-style
services around autonomous AI applications.

The implemented system

combines a Next.js user interface, a FastAPI gateway, a Redis-backed event
path, MongoDB task history, ChromaDB semantic retrieval, structured LLM
planning, dependency-aware directed acyclic graph execution, semantic context
paging, a global priority-aging scheduler, token and concurrency admission
control, and a sandboxed Python code runner with bounded self-healing retries.
The frontend exposes the generated plan graph and live scheduler and execution
activity through WebSocket updates. The report distinguishes implemented
facilities from proposed components such as complete role-based access control,
hybrid model routing, and durable coroutine restoration after a kernel restart.
Verification is based on repository compile checks, TypeScript checks, and
focused smoke tests rather than unsubstantiated performance claims. AgentOS
therefore provides a modular foundation for studying reliable, observable, and
resource-aware multi-agent execution.
Keywords: multi-agent runtime, semantic planning, DAG execution,
context paging, priority scheduling.

CHAPTER 1
INTRODUCTION

1.1

BACKGROUND

Large-language-model (LLM) applications have progressed from
reactive question-answering interfaces to systems that can plan, call tools,
maintain memory, and delegate work to specialised agents. A useful multi-agent
application therefore needs more than a prompt and a model endpoint. It needs a
runtime that can represent work, enforce dependencies, manage limited provider
and execution resources, preserve useful context, report progress, and recover
safely from failures.
Operating-system concepts provide a useful design analogy. A task
is submitted to a gateway, a planner decomposes it into executable steps, a
scheduler selects runnable agent work, a resource manager performs admission
control, and an event path exposes state transitions. AgentOS applies this
analogy to LLM-powered agents while retaining the uncertainty and latency of
model calls.

1.2

MOTIVATION

In a conventional chatbot, application logic, conversation state, tool
invocation, and error handling are often tightly coupled. This makes it difficult
to run independent work concurrently or to explain why an agent was selected.
Long conversations also exceed the practical context window of a model, while
blindly truncating history can remove information needed by later steps. Finally,
direct code execution or unrestricted tools create safety and observability risks.

2
AgentOS is motivated by the need for a reusable runtime layer. The
project investigates how planning, agent retrieval, DAG execution, semantic
context paging, global scheduling, resource accounting, event streaming, and
sandboxed execution can be composed into one observable system.

1.3

PROBLEM STATEMENT

There is no single lightweight runtime in the project environment
that coordinates heterogeneous agents across multiple concurrent tasks
while enforcing dependencies, observing token and concurrency budgets,
preserving relevant context, and exposing execution state to a user interface.
Reimplementing these facilities inside each application increases duplication,
makes failures difficult to diagnose, and prevents systematic evaluation of
scheduling and resource policies.

1.4

OBJECTIVES

The objectives of AgentOS are:

1. Develop a modular AI-kernel-style runtime for specialised agents;
2. Generate structured execution plans, retrieve suitable agents
semantically, and validate their dependencies as a DAG;
3. Manage bounded conversational context through semantic page-out
and page-in using a vector-backed swap space;
4. Schedule runnable work with priority aging, fairness, cooperative
dispatch, concurrency limits, and token budgets; and
5. Execute agent and code-runner tasks reliably while publishing
lifecycle events and measurable activity to the user interface.

3
1.5

SCOPE

The current phase covers a Next.js frontend, FastAPI gateway,
Python kernel, Redis event transport, MongoDB task persistence, ChromaDB
retrieval, structured planning, DAG validation and Mermaid generation, context
paging, a global in-process scheduler, resource admission, and a sandboxed
Python runner.

The scope does not claim complete RBAC, distributed

scheduler workers, forced termination of active LLM calls, automatic coroutine
restoration, or a production-grade hybrid model router. These are documented
as future work.

1.6

CONTRIBUTIONS

The project contributions are a unified execution model for
heterogeneous agents, a visible plan graph, a Redis-mediated activity stream,
a semantic context paging mechanism, a priority-aging scheduler with
resource admission, and a bounded code-execution/self-healing path.

The

implementation also makes a deliberate distinction between design aspirations
and features that are present and testable in the repository.

1.7

REPORT ORGANIZATION

Chapter 2 surveys research and technical systems related to
autonomous agents, memory, planning, scheduling, tool use, security, event
transport, and vector retrieval. Chapter 3 presents the AgentOS architecture
and data flows. Chapter 4 describes the implementation algorithms, storage
conventions, events, and verification evidence. The conclusion records current
limitations and future extensions.

CHAPTER 2
LITERATURE SURVEY

2.1

OVERVIEW

This chapter reviews work that informs the design of AgentOS.
The survey combines peer-reviewed or archival research with official technical
documentation for infrastructure components. Each group is considered in terms
of its contribution, limitation for the present project, and the way AgentOS uses
or extends the idea.

2.2

AGENT RUNTIMES AND AUTONOMOUS AGENTS

AIOS frames an LLM agent operating system around scheduling,
context management, memory, storage, access control, and tool management
[1].

Its operating-system analogy directly motivates the AgentOS kernel,

although the current AgentOS implementation is smaller and uses a
Python/Redis/MongoDB stack rather than a complete OS abstraction. The
broader survey by Wang et al. classifies LLM-based agents by construction,
applications, and evaluation [2]; it identifies coordination and reliability as
open challenges that AgentOS addresses through explicit events and DAG
dependencies.
The LLM-as-an-OS proposal treats models as system resources and
agents as applications [3]. AutoGen demonstrates programmable multi-agent
conversation and human-in-the-loop patterns [4], while LangGraph provides
graph-based orchestration and durable execution concepts [5]. These systems

5
show the value of explicit state and orchestration, but do not provide the exact
global priority-aging and token-admission policy implemented here.

2.3

MEMORY AND CONTEXT MANAGEMENT

MemGPT introduces virtual context management that moves
information between active context and external storage [6].

MemoryOS

organises memory into short-, mid-, and long-term layers and evaluates
memory retention for conversational agents [7].

These works motivate

AgentOS context page-out and page-in. AgentOS uses semantic embeddings in
ChromaDB and an active-window policy; it currently provides a project-level
paging mechanism rather than a learned memory hierarchy or an independently
benchmarked memory score.
Retrieval-Augmented Generation (RAG) combines generation with
a non-parametric knowledge store [8].

ChromaDB documents collections,

embeddings, and distance-based retrieval [9]. AgentOS uses this pattern both
for agent capability retrieval and for swapped context. The limitation is that
retrieval quality depends on the embedding model and distance configuration;
the current implementation exposes similarity metadata but does not claim
domain-wide retrieval benchmarks.

2.4

PLANNING, TOOL USE, AND REFLECTION

ReAct interleaves reasoning and action so that an agent can use
external tools during problem solving [10]. Toolformer studies self-supervised
learning for deciding when and how to call APIs [11]. Generative Agents
combine memory, reflection, and planning for believable behaviour [12].
Reflexion uses verbal feedback to improve subsequent attempts without

6
updating model weights [13]. AgentOS adopts structured planning, explicit
tool boundaries, persisted events, and bounded self-healing, but does not
train models or claim the autonomous reflection capabilities of these research
systems.
The Transformer architecture remains the dominant basis for modern
LLMs [14]. Its context limitation makes external context management relevant
to AgentOS, while the model itself remains an external provider selected by the
planner/runtime.

2.5

SCHEDULING, RESOURCES, AND RELIABILITY

Classical operating-system scheduling shows why priority alone can
starve old work and why aging can improve fairness [15]. Linux cgroups
provide a practical model for resource accounting and isolation [16]. AgentOS
adapts these ideas to agent work: effective priority increases with queue wait,
admission checks global and per-task slots, and token reservations are tracked
before dispatch. Unlike a CPU scheduler, AgentOS cannot forcibly preempt an
in-flight remote LLM request; its quantum is cooperative and checkpoint-based.
The workflow and orchestration literature emphasises explicit
dependency graphs and stateful execution. LangGraph persistence documents
checkpointed graph state [17], while Temporal documents durable workflow
execution [18]. AgentOS currently validates and executes a DAG in-process
and persists task/event evidence; automatic continuation of interrupted
coroutines remains future work.

7
2.6

SECURITY AND SANDBOXED EXECUTION

The Model Context Protocol specifies a standard way for AI
applications to connect models with tools and data sources [19]. OWASP’s
LLM security guidance highlights risks including excessive agency, insecure
tool use, and code execution [20]. Python subprocess execution and filesystem
scoping are therefore bounded in the code runner. Firecracker demonstrates the
stronger isolation achievable with microVMs [21]. AgentOS’s current runner
limits duration and output and scopes its working directory, but it is not a
substitute for a hardened kernel or microVM sandbox.

2.7

EVENT-DRIVEN INFRASTRUCTURE

Redis documents Pub/Sub as a low-latency message distribution
mechanism [22]. MongoDB provides durable document storage suitable for
task history and metadata [23]. AgentOS uses Redis for transient task/event
transport and queue metadata and MongoDB for durable task records. Redis
Pub/Sub alone is not a durable event log; recovery therefore persists relevant
state in Redis hashes and MongoDB events, with full replay and exactly-once
semantics left for future work.

2.8

RESEARCH GAP AND POSITIONING

The reviewed systems provide strong solutions for individual
concerns:

planning, memory, graph orchestration, tool use, security,

or workflow durability.

AgentOS’s contribution is an integrated

educational/runtime prototype that makes these concerns observable
together in one project. Its distinctive implementation choices are semantic
agent selection, explicit DAG validation, global priority-aging scheduling,

8
token/concurrency admission, Redis lifecycle events, context paging, and
frontend graph/activity observability. The current phase prioritises a transparent
and testable architecture over claims of production isolation or benchmark
leadership.

CHAPTER 3
SYSTEM DESIGN

3.1

DESIGN PRINCIPLES

AgentOS is designed as a modular runtime. The gateway handles
external requests, the orchestrator converts a prompt into a structured plan, and
the kernel owns execution concerns. Redis is used for low-latency coordination
and event transport, while MongoDB stores task history. ChromaDB stores
embeddings used for semantic agent retrieval and context swap. The design
keeps the current dependency truth in the DAG executor and treats scheduler
decisions as admission and dispatch decisions.

3.2

OVERALL ARCHITECTURE

As shown in Figure 3.1, AgentOS is organised as an overall
runtime architecture connecting the user interface, gateway, planner, kernel,
storage, tools, agents, and model engines. The figure combines implemented
runtime components with architectural modules that are planned or only
partially implemented; their implementation status is documented separately in
Section 3.11. A user submits a task through the Next.js interface. The FastAPI
gateway creates or retrieves task state and communicates with the kernel. The
planner selects agents and creates steps; the kernel validates and executes those
steps while publishing activity events.

PLANNER AND DAG EXECUTION

The planner retrieves relevant agent descriptions, requests a
structured execution plan, and applies a fallback plan when the provider is
unavailable. Each step includes an identifier, agent name, description, and
dependency list.

The validator canonicalises identifiers, rejects unknown

dependencies and cycles, and supplies a sequential fallback only when a
plan omits dependencies. The executor runs only steps whose prerequisites
are complete. Figure 3.3 summarises this path. The frontend uses the same
validated plan to generate Mermaid source and draw the plan graph, ensuring
that displayed edges represent dependencies rather than decorative links.

3.5

CONTEXT PAGING

The context pager keeps a bounded active message window. When
the window is exceeded, older or less relevant messages are embedded and
stored in the ChromaDB swap collection. A later query retrieves semantically
related pages and injects them into the active context. ChromaDB’s cosine space
returns distance; the implementation converts it as s = 1 − d, where d is the
returned cosine distance. Figure 3.4 presents the page-out and page-in flow.
This mechanism reduces active prompt growth but does not guarantee perfect
recall.

3.6

GLOBAL SCHEDULER AND RESOURCE MANAGER

The scheduler maintains ready records and selects work globally

14
across active tasks. Effective priority is computed from base priority and queue
waiting time, bounded by a maximum. Before dispatch, the resource manager
checks the global slot limit, per-task slot limit, and token budget. The current
defaults are three global execution slots, two slots per task, and a configurable
50,000-token task budget. Dispatch is cooperative: a running remote LLM
request is not forcibly killed. Figure 3.5 shows the decision path.

3.10

SANDBOXED CODE RUNNER

The code runner receives generated Python, writes it into a scoped
working directory, and invokes it through an asynchronous subprocess. It
bounds execution time and captured output. A non-zero exit code or traceback
is returned to the coder/tester agent, which may produce a corrected version
for at most three attempts. Output lines can be published as kernel events for
live frontend observation. Figure 3.9 shows this flow. The current isolation
is process and directory scoping; hardened container or microVM isolation is
future work.

CHAPTER 4
IMPLEMENTATION

4.1

IMPLEMENTATION ENVIRONMENT

The kernel is implemented in Python using asynchronous services.
The backend is FastAPI-based and the frontend is implemented with Next.js
and TypeScript. Redis provides task/event channels and scheduler metadata;
MongoDB stores task records and event history; ChromaDB provides persistent
vector collections for planning and context swap. Provider-specific LLM usage
is treated as optional metadata because some providers do not return reliable
token counts.

4.2

SEMANTIC AGENT RETRIEVAL

Agent descriptions are embedded in a persistent ChromaDB
collection. A task description is used as a query, and the top candidate records
are returned with their distances and metadata. In the configured cosine space,
ChromaDB returns d = 1 − cos(θ), so the implementation reports s = 1 − d.
It does not divide by two; that transformation would be appropriate for a
different distance normalisation. An LRU cache reduces repeated retrieval for
identical descriptions. Algorithm 4.1 summarises this candidate-retrieval and
cosine-distance conversion procedure.

4.3

PLANNER AND FALLBACK

The planner asks the configured LLM for a structured execution plan.
The response is parsed into steps and normalised against the agent registry. If the
LLM request fails, exceeds quota, or produces invalid structure, a deterministic
fallback creates a usable plan from the best retrieved agent(s). This maintains
task execution and observability without pretending that the fallback has the
same reasoning quality as the provider.

semantic candidate retrieval through structured plan validation, fallback routing,
DAG construction, scheduling, and runtime execution.

4.4

DAG VALIDATION

Every step has a unique identifier and a list of prerequisite
identifiers. Validation rejects duplicate identifiers, unknown agents, unknown
dependencies, and cycles. A Kahn-style topological pass counts nodes removed

CONTEXT PAGE-OUT AND PAGE-IN

The pager moves messages from the active conversation state to a
persistent ChromaDB collection after a configured window is exceeded. Each
page stores message content, task metadata, and an embedding. On a later turn,
the current query is embedded and the collection is searched; selected messages
are reintroduced in relevance order. The implementation emits page-out and
page-in metrics, allowing the UI or logs to verify that paging occurred.

4.9

SANDBOXED EXECUTION AND SELF-HEALING

The code runner creates a scoped temporary script, launches it with
asyncio.create subprocess exec, captures stdout/stderr, and terminates the
subprocess after a strict timeout. Output size is limited to prevent unbounded
memory use. On a traceback, the error is supplied to the coder/tester agent and a
revised script is attempted, up to three times. The runner publishes line-oriented
output and final status as kernel events. No claim is made that an ordinary
subprocess is equivalent to a container or microVM security boundary.

The task activity panel displays lifecycle events, scheduler state,

decisions, and token totals when provider metadata is present.

The plan

graph modal displays the structured graph and Mermaid source. Token fields
distinguish input, output, total, and configured budget; when the provider omits
usage, the interface reports that the metadata is unavailable rather than inventing
a count.

CHAPTER 5
RESULTS AND PERFORMANCE ANALYSIS

This chapter reports the planner’s model-backed tool-selection
evaluation.

The experiment evaluates whether the model can select the

registered AgentOS agent functions needed to execute a task. It is deliberately
distinguished from the official Berkeley Function Calling Leaderboard (BFCL):
the benchmark cases, tool catalogue, and expected agent mappings are
AgentOS-specific.

The evaluation is therefore reported as an AgentOS

tool-selection adapter study rather than as a BFCL leaderboard score.

5.1

EXPERIMENTAL CONFIGURATION

The evaluation used the AgentOS function catalogue generated
from the registered agent registry. Each registered agent was exposed as an
OpenAI-compatible function with a task argument and an optional context
argument. The model endpoint was Groq using openai/gpt-oss-120b. The
same catalogue and system prompt were used for every trial. Because every
task in this dataset required at least one registered agent, the request used
required tool-call mode. A 25-second inter-request delay was applied to avoid
token-per-minute throttling.
The 50-trial evaluation covered nine task categories: date and
time, system information, weather, research, code execution, email delivery,
multi-agent coordination, financial calculation, and document workflow.
Category sample sizes ranged from five to six trials.

The evaluation is

intended as a reliability-oriented project benchmark rather than as a statistically
representative estimate of general function-calling ability.

34
5.2

EVALUATION MEASURES

Exact tool-set accuracy is the fraction of trials for which the selected
agent functions exactly matched the expected set. Required-tool recall is the
fraction of trials in which every expected function was selected. The end-to-end
measures count a failed model tool call as an incorrect outcome. Provider
errors and model tool-call failures are recorded separately so that infrastructure
problems are not confused with routing errors.

5.3

RESULTS

the expected tool set, while twelve trials failed at the tool-call stage. No provider
errors were recorded. The aggregate latency, computed from the category-level
means weighted by their trial counts, was 1003.36 ms.

the evaluation uses the AgentOS registry, a project-specific task set, and
AgentOS-specific expected tool mappings. The aggregate score includes all 50
trials and therefore incorporates the 12 tool-call failures. The more informative
system-level result is consequently 38 correct outcomes out of 50 total trials,
together with a 24.0% tool-call failure rate and zero provider errors.

an external model-level comparison, but it should remain separate from this

6.9

REPORTING PROTOCOL

The evaluation shall use a fixed task set and a documented procedure
for every configuration.

1. Define and repeat the test. Record the prompts, expected outputs,
required agents, dependency relations, configuration, number of

46
tasks, and number of independent repetitions. Keep the planner
model, candidate limit, context window, scheduler limits, resource
limits, and retry policy fixed within a comparison.
2. Record raw evidence. Store the task identifier, prompt, expected
result, candidates, generated plan, validation result, lifecycle events,
attempts, timestamps, resource decisions, token metadata, and final
status. Retain raw events so metrics can be recomputed.
3. Compute task-level outcomes. Mark a trial as successful only when
the expected result is produced and all mandatory steps complete.
Record whether the trial failed, waited, was retried, used fallback
planning, violated dependency order, or exceeded a resource limit.
4. Aggregate and report. Report accuracy, success, failure, retry,
fallback, and violation measures as percentages. For latency, queue
waiting time, token usage, and other continuous measurements,
report the mean, median, standard deviation, and 95th percentile
(P95 ), together with the number of trials and tasks.
For a rate, use the pooled value 100 × (∑ numerator/ ∑ denominator)
and state how missing or timed-out observations were handled. A
zero denominator must be reported as not applicable, not as zero.
5. Document annotations and usage. Explain labels for expected
agents or relevant context pages, including the annotation procedure
and number of labelled tasks. Distinguish provider-reported token
usage from estimated admission usage.

Each configuration summary should therefore include task and
repetition counts, success or accuracy rate, failure and retry rates, latency
statistics, and relevant scheduler, resource, context-paging, and token-usage
measures. No experimental values are reported in this appendix.

CHAPTER 7
CONCLUSION

This project presented AgentOS, a modular runtime for multi-agent
applications in which planning, semantic agent selection, DAG execution,
context management, scheduling, resource admission, sandboxed code
execution, and frontend observability are treated as shared system services. The
implemented system connects the Next.js interface, FastAPI gateway, Python
kernel, planner, Redis event path, MongoDB task history, ChromaDB retrieval,
scheduler, resource manager, agent runtime, and frontend activity interface into
one observable execution pipeline.
The implementation demonstrates that operating-system-inspired
services can be composed around heterogeneous agents without placing
scheduling, memory, execution, and observability logic inside each individual
agent.

Structured plans and dependency validation provide predictable

execution order; semantic context paging reduces the prompt context presented
to the model; priority aging and resource admission coordinate runnable work;
and bounded subprocess execution provides a controlled path for coding and
testing tasks. The frontend activity stream makes these decisions visible to the
user.
The current implementation also has defined limitations. Scheduler
dispatch is cooperative, provider token usage may be unavailable when metadata
is omitted, and restart recovery detects interrupted work without restoring every
active coroutine. Evaluation results should therefore be interpreted together with
their dataset scope, provider conditions, and telemetry coverage rather than as
universal claims of system performance.

48
Future work will focus on durable restart resumption, true
checkpoints inside long-running agents, complete capability enforcement,
a hybrid local/cloud model router, cost-aware scheduling, production-trace
scheduler evaluation, stronger external function-calling evaluation, and
additional autonomous event triggers.

These extensions can be added

without changing the central separation between planner, scheduler, runtime,
persistence, and observability layers.
